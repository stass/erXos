# Protocol verification

Protocol decisions are handwritten pure C17 or Erlang functions: a state
and an event produce a next state and explicit actions. Thin effect layers
perform those actions and return their outcomes as events. Host tests
exercise the same decision code that runs on the target. Independent
TLA+ models, checked with TLC, describe the protocol and its properties.
The subsystem designs own the contracts; this document owns how the
evidence is constructed and connected to the implementation.

## Models and implementations

Models have two useful grains. An abstract protocol model treats a
complete operation as one action to check ownership, authority and
lifetime rules. A mechanism model separates the publication, observation
and completion steps where other agents or failures can intervene. An
atomic abstract action is justified by the implementation's mechanism or
by a separate mechanism model; an abstract pass alone cannot establish
that a concurrent implementation is correct.

Each model states its complete configuration, initial states, actions,
invariants, environmental assumptions and finite bounds. Relevant pending
work, ownership and persisted state are explicit. A crash can occur
between durability steps, and a timeout is an event, not evidence that
the other party stopped. Safety checks admit starvation and failures;
liveness checks separately name the fairness, scheduling and device
progress assumptions they require. The checked property is not used as
a state constraint that removes its own counterexamples.

TLA+ and optional PlusCal are host specifications, chosen to express
interleavings and temporal properties directly. They generate no target
protocol implementation. Small transition tables may be generated by
Ruby where they improve readability, but their expected answers and
properties have an independent source. Service interfaces, inspection
projections, error translations, reference tables and parser test/fuzz
scaffolding follow [Generated interfaces and representations](design-generation.md).
Wire layouts and codecs retain the ABI's one source; a general protocol
language is not required.

The first worked model is the update protocol: committed and spare slots,
healthy trials, persisted writes, torn records, resets and rescue. It is
small enough to inspect and has concrete failure-injection tests. Host-link
sessions and connection retirement use the same discipline. Small kernel
cores retain exhaustive host exploration; additional TLC mechanism models
address interleavings that their subsystem designs identify.

## Model suite and runner

The setup follows the OpenBDB model-suite approach: a JVM and the TLA+
tools jar, `.tla` modules with `.cfg` configurations, an expectation roster,
and an invariant-to-implementation mapping. Models live in `specs/tla/`;
`README.md` explains their scopes and `MAPPING.md` maps every property to
its owning design, implementation functions and concrete test or assertion.
Those files document the models, not another version of the architecture.

The top-level `make check-tla` invokes a Ruby runner through `tools/erx`.
It is a separate gate from ordinary `make check`. Changes to a model,
configuration, runner, or a mechanism represented by a model run the
affected configurations; release validation runs the whole suite uncached.
A mechanism change updates its model and mapping in the same change, or
explains in the commit why the abstraction and checked properties hold
unchanged. Changes outside modeled mechanisms do not require a TLC run.

`TLA_TOOLS_JAR` selects `tla2tools.jar`; the macOS default is
`/Applications/TLA+ Toolbox.app/Contents/Eclipse/tla2tools.jar`, as in
OpenBDB. A JVM is a host prerequisite installed through Homebrew. The
jar's accepted version and SHA-256 are pinned before use; an override
selects a location, not permission to use different bytes. The runner
checks the jar hash and records the Java version. Missing or mismatched
tools fail a requested check with a diagnostic; no tool is downloaded
during a check. The explicit fetch step can supply the pinned jar on
hosts without the Toolbox installation.

Each roster entry names a module, configuration, translation kind and
expectation. Every configuration belongs to exactly one entry; duplicate,
missing and unregistered entries fail before checking, even for a filtered
run. A filter matching no entry fails. Good configurations require both a
successful tool exit and its completed-check result. A broken configuration
enables one intentional fault and must fail on its named property; a parser error, wrong property,
out-of-memory result or timeout is never that expected failure. The runner
matches the exact property identity and the tool's expected failure status,
not a substring that could occur in an unrelated diagnostic. Reachability
configurations deliberately falsify a named "not reached" invariant to
witness important paths. Bounds preserve the distinct owners and events
needed for those witnesses rather than merely keeping the run cheap.

Every run snapshots its model inputs into a private work directory. PlusCal
translation runs there before checking; generated translations have a drift
check against the checked-in module. Concurrent runs never rewrite source
files. Each TLC process has its own metadata directory, Java temporary
directory and log. `TLA_JOBS`, `TLA_WORKERS` and `TLA_JVM_MEM` control the
pool, workers and heap; the runner bounds aggregate memory and records the
resolved settings. It invokes Java by argument vector, with closed stdin
and a hard `gtimeout -k 10` deadline, and ends every process it started on
failure or cancellation. Logs are checked for progress after 30 to 60
seconds; live status reports each command's age and deadline.

Deadlock checking is enabled unless a safety-only configuration explicitly
declares terminal states acceptable. TLC's `-deadlock` option disables
that check; it is not a suite-wide default. Liveness configurations name
their temporal properties and fairness assumptions. Reports distinguish
a completed finite-state search from a depth-limited or constrained one.

Caching reuses only results that met their expectations. A key covers the
model's complete module closure, configurations, expectations, runner,
jar hash, Java identity and effective checking flags; an unresolved input
disables caching. `TLA_NO_CACHE=1` bypasses it. Output separates checked,
cached, failed and incomplete configurations, with elapsed times and raw
logs. A cached result retains its original evidence. Timeouts, resource
exhaustion and tool errors fail the gate and never become green cache
entries. Runner tests include each of those outcomes and incorrect
expected-failure matches.

## Evidence against the implementation

Each mapping names the implementation state represented by model variables,
the actions represented by calls or observable effects, and the assumptions
left to hardware or external services. Multi-step calls can correspond to
several model actions; unobservable steps may leave the model unchanged.
The mapping is reviewed and tested, not claimed as a mechanical refinement
proof. TLC counterexamples become host regression traces and, where they
cross the effect boundary, QEMU failure-injection tests.

The host harness compares the implementation's decisions and observable
outcomes with an independent C, Erlang or Ruby reference oracle of the
contract, over the stated finite configurations and event orders. TLC
runs separately; its counterexample traces are translated into inputs for
this harness. The harness checks state properties
after every step and exercises failure outcomes as well as success. A
shared helper can support exploration, but it cannot supply both the
implementation decision and its independent expected answer. Stateful
property tests complement exhaustive exploration for larger configurations;
they record seeds and minimize failing operation sequences.

TLC checks the model, not machine-code execution, memory safety, real
durability or hardware memory ordering. Sanitizers, independent OTP and
POSIX oracles, crash tests, hardware conformance and `herd7` weak-memory
litmus tests retain their roles. TSan detects data races; it does not
establish acquire/release protocol correctness. Every report states the
bounds, assumptions and model-to-code gap with its result.

## Focused tool evaluations

The roadmap owns the adoption decisions for these pilots. They extend
verification behind existing interfaces and do not change runtime authority.

* **CBMC on the C core.** Check the actual budget arithmetic and capability
  retirement functions with nondeterministic inputs and explicit allocation
  failure. The harness states input ranges, compiler layout assumptions,
  scheduling assumptions and loop bounds; unwinding assertions detect
  insufficient loop coverage. A bounded result is reported as bounded.
  Unsupported C17 constructs or target differences are explicit gaps.
* **awklog on manifest relationships.** Ruby parses and validates the
  manifest and platform placement records, then emits typed facts with
  source-record identities. awklog checks device ownership, facet targets,
  boot-order cycles and rescue closure against an independent Ruby oracle
  over small configurations. Ruby retains checked exact arithmetic for
  budget and grant sums: awklog has no arithmetic and its numeric values
  do not represent every 64-bit integer exactly. Full-width identifiers
  are strings. No decision treats a pid or a facet edge as universal
  transitive authority: only the particular operation's declared rights
  and delegation rules justify a path. Unknown records, malformed output
  or tool failures refuse the build. Runtime capability lookup and service
  admission remain authoritative for dynamic operations.

The awklog experiment uses the existing manifest check's inputs and
diagnostics. It must preserve seeded rejection tests for every manifest
property. It is adopted only if the relational rules make those checks
clearer without a second source of policy. Unmodified tools stay outside
the source tree at pinned versions and hashes and run only as subprocesses.
