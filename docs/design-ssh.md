# SSH

A person on another machine runs `ssh root@erxos` and gets a shell in a
session of their principal, holding exactly that session's grants, as a
login at the console gives. OTP's `ssh` daemon serves the protocol in a
configured domain of its own, the **SSH domain**, which parses what the
network sends; the system domain decides who logs in; the vault holds the
host key and each principal's login keys; and the shell runs in the
principal's session, on a tty whose master is the SSH channel. The
cryptography underneath is [design-crypto.md](design-crypto.md).

## Context

The roadmap puts SSH in M14, over erXos's own TCP/IP stack on QEMU in
1b-G, then on the boards ([plan.md](plan.md#1b-g-networking-on-qemu)),
with the host key signed by the vault's key facet at M12's keys
([plan.md](plan.md#m12-storage-networking-boards)). The designs it rests
on:

* **Principals and sessions.** A session is started by a login and made
  from its principal's session template alone; it is its facets and its
  session domain, whose sub-spaces are the principal's programs
  ([design-domains.md](design-domains.md#principals-sessions-and-quotas)).
* **The web's precedent.** The web domain is a configured domain that
  parses browsers' bytes and holds the system domain's `erx_web_login`
  facet: a login hands a name and passphrase to the principal service,
  the vault checks it, the domain service starts a session, and the
  system domain introduces the session to the web domain
  ([design-web.md](design-web.md#logging-in-and-the-line)).
* **Ttys and masters.** A session's ttys live in its terminal relay. A
  tty's master is the console, a terminal of the session, or a
  pseudo-terminal's holder, and a tty and a master in another domain
  exchange six closed messages, `tty_open`, `tty_output`, `tty_taken`,
  `tty_input`, `tty_size` and `tty_hangup`, each checked by its receiver;
  a master in another domain is heard only through its domain's envelope;
  at `tty_hangup` the relay ends the tty's shells
  ([design-live.md](design-live.md#paths)).
* **Pipes stay in the session.** A pipe's ends are held by the session's
  processes and programs; a process of another domain holds none, and a
  command domain's streams are relayed by a process of the session over
  the session's connection to it
  ([design-programs.md](design-programs.md#what-a-program-can-start),
  [design-pipes.md](design-pipes.md#the-sessions-pipe-nif)).
* **The vault.** Its `{ssh_host, Name}` facet signs exchange hashes and
  never gives the key away; it signs any input of 32, 48 or 64 bytes,
  since an exchange hash has no other structure to check; machine keys
  live in the machine's file and are made afresh at each installation;
  while a session of a principal lives, the vault keeps that principal's
  master key and opened keys, and destroys them when the last one ends;
  erXos's `ssh` adds `host_key/2` returning `{ok, {ssh2_pubkey, Blob}}`
  and an optional `sign/3` to the daemon's key API
  ([design-system.md](design-system.md#the-vault)).
* **The network grant.** A grant lists the ports it may bind, ports
  below 1,024 only when listed, and whether it may listen, with limits on
  sockets and buffers
  ([design-network-stack.md](design-network-stack.md)).

What the sources say, read at the pins of [Sources](#sources):

* **The session identifier is the first exchange's hash.** The exchange
  hash is `HASH(V_C || V_S || I_C || I_S || K_S || e || f || K)`: both
  sides' version lines, both sides' `SSH_MSG_KEXINIT` payloads, the
  server's host key, both exchange values and the shared secret, each
  length-prefixed (RFC 4253, section 8). The hash of the first exchange is
  the session identifier and never changes (section 7.2). Every
  `SSH_MSG_KEXINIT` begins with a 16-byte cookie that "MUST be a random
  value generated by the sender" (section 7.1). The client checks that
  `K_S` is the host key for the server it dialled and verifies the host
  key's signature over the hash before it goes on (section 8, step 3). A
  `publickey` signature covers the session identifier, the message
  number, the user, the service, the method, `TRUE`, the algorithm and the
  key, and nothing else of the server's (RFC 4252, section 7).
* **OTP builds that input and keeps its hash, not the input.** The server builds
  the hash input in `kex_plaintext/3`, five strings followed by what the
  exchange method adds (`lib/ssh/src/ssh_transport.erl:2318-2323`); for
  the ECDH and Curve25519 methods that is `Q_C` and `Q_S` as strings and
  `K` as an mpint (`:2332-2334`), for `mlkem768x25519-sha256` `C_INIT`
  and `S_REPLY` as strings and `K` already encoded (`:2325-2331`). The
  server keeps the hash and the encoded `K` and drops the rest
  (`:905-907`, `:988-990`). Its
  cookie is `ssh_bits:random(16)` (`:353`). `verify_sig/7` builds the
  signed data of RFC 4252 section 7 from the stored session identifier
  (`lib/ssh/src/ssh_auth.erl:583-592`).
* **OTP 29.1.2's daemon serves nothing by default**: `subsystems`
  defaults to `[]`, `shell` and `exec` to `disabled`, `tcpip_tunnel_in`
  and `tcpip_tunnel_out` to `false` (`lib/ssh/src/ssh_options.erl`,
  `default(server)`, `:419`, `:465`, `:471`); `max_sessions` is 1,024,
  `max_channels` 256, `parallel_login` false, `negotiation_timeout` 120 s
  and `hello_timeout` 30 s (`:584-612`). With `parallel_login` false, the
  acceptor starts each connection in its own loop and waits for that
  connection's authentication, up to `negotiation_timeout`, before it
  accepts the next (`ssh_acceptor.erl:108-111`, `ssh_system_sup.erl:127`,
  `ssh_connection_handler.erl:124-140`, `:495-513`). It has no option
  bounding the authentication attempts of one connection. A channel's
  window is ten packets of 64 KiB (`lib/ssh/src/ssh_connect.hrl:27-28`).
* **OTP checks a public key in the daemon's own process**:
  `ssh_auth:verify_sig/7` asks the key callback's `is_auth_key/3`, builds
  the signed data and verifies it there, with the algorithm required to
  be in the daemon's `preferred_algorithms` (`ssh_auth.erl:565-581`). The
  daemon reads its host key through `host_key/2`
  (`lib/ssh/src/ssh_server_key_api.erl:61`, `ssh_transport.erl:1111`).
  A terminating connection's status report omits the key exchange's
  secrets by a list of `#ssh{}` fields in `clean/1`
  (`ssh_connection_handler.erl:1604-1605`, `:1616-1635`); a normal one,
  as `sys:get_status/1` asks for, returns the state unchanged (`:1602-1603`).
  Each connection's handler keeps the first exchange's hash as the
  session identifier and never replaces it at a rekeying (`sid/2`,
  `ssh_transport.erl:1105-1106`). User authentication succeeds for every
  method through one function, `connected_state/5`
  (`ssh_fsm_userauth_server.erl:173-181`). `verify_sig/7` takes the
  signature field apart into the signature blob, `AlgSig`, which holds the
  algorithm name and the signature, and the bare signature inside it
  (`ssh_auth.erl:574-576`).
* **OTP negotiates the strict key exchange** that closes the Terrapin
  prefix truncation when both sides offer it, and connects a peer that
  does not offer it without it (`ssh_transport.erl:311`, `:538-550`); it
  sends `server-sig-algs` (`:1068`, `:1095`).
* **OpenSSH's privilege separation** takes the session identifier from
  the first hash its host key signs for a connection
  (`crypto/openssh/monitor.c:767-772`) and checks a user's signed data
  against it (`:1366-1393`); its own comment says it cannot check the
  exchange behind the hash, "since what is signed is the hash, rather
  than the full kex structure" (`:739-741`).
* **Ed25519 verification** is RFC 8032's (RFC 8709, section 7): `S` lies
  in `0 <= S < L`, `R` and the public key decode as points, which fails
  when `y >= p`, when no square root exists, or when `x = 0` with its sign
  bit set, and the group equation holds, with or without the cofactor
  (RFC 8032, sections 5.1.3 and 5.1.7).
* **FreeBSD's sshd** (OpenSSH 10.0, `FreeBSD-20250801`, in
  `crypto/openssh/`): its server key exchanges are
  `mlkem768x25519-sha256`, `sntrup761x25519-sha512` in two names,
  `curve25519-sha256` in two names and `ecdh-sha2-nistp256`, `-384`,
  `-521`, with no finite-field group (`myproposal.h:27-35`); its ciphers
  `chacha20-poly1305@openssh.com`, `aes128-gcm@openssh.com`,
  `aes256-gcm@openssh.com` and `aes128-ctr`, `aes192-ctr`, `aes256-ctr`
  (`:61-64`); its MACs the UMAC and HMAC-SHA-2 and HMAC-SHA-1 families,
  `-etm` first (`:68-78`); its user key algorithms Ed25519, ECDSA and
  `rsa-sha2-512`, `rsa-sha2-256`, no `ssh-rsa` (`:43-59`). Its defaults:
  `LoginGraceTime` 120, `PermitRootLogin no`, `PasswordAuthentication no`
  with `KbdInteractiveAuthentication yes` through PAM,
  `MaxStartups 10:30:100`, `X11Forwarding no`, `PermitTunnel no`,
  `AllowTcpForwarding` and agent forwarding allowed
  (`servconf.c:300-480`), `MaxAuthTries` 6 and `MaxSessions` 10
  (`servconf.h:39-40`); its `sshd_config` sets
  `AuthorizedKeysFile .ssh/authorized_keys` and the `sftp` subsystem
  (`sshd_config:44`, `:117`).

## Requirements

* **S1.** A login gets exactly its principal's session: the session's
  facets are its template's, and nothing of the SSH domain's authority
  passes to it.
* **S2.** The SSH domain cannot start a session on its own word: who
  logs in is decided outside it, from a passphrase the vault checks, or
  from a signature by one of the principal's login keys over a session
  identifier that the deciding side derives itself, from an exchange that
  carried a cookie the deciding side chose and this machine's host key.
* **S3.** The system domain never runs OpenSSL, and neither it nor the
  vault parses an SSH packet: what reaches them from the network is a few
  bounded values, each of one purpose, and the system domain's one decoder
  of them reads only fixed-format Ed25519 key and signature blobs and the
  five length-prefixed strings that begin an exchange's hash input; the
  vault decodes no SSH structure at all ([Logging in](#logging-in)).
* **S4.** Text from the network reaches a log only through the log
  sink's escaper.
* **S5.** What a connection can make the machine spend is bounded, and
  charged to the SSH domain or to the principal's session.
* **S6.** The algorithms offered are fixed by configuration, with no
  SHA-1 signature, CBC cipher or finite-field exchange.
* **S7.** Clients see one host key per installation, the same across
  reboots and updates.

## What the code does today

Nothing of SSH exists: `crypto`, `public_key`, `asn1` and `ssh` are
outside the imported OTP ([design-crypto.md](design-crypto.md#what-the-code-does-today)),
no SSH domain is in any manifest, and `abi/services/` declares no login
service for it. TCP through a domain's `net` grant works on QEMU for
connections the domain opens; root's session holds such a grant in
development builds (`README.md`, the network paragraph).

## Design

### An SSH connection is a line

The construction: **an SSH connection is a login line, and each of its
channels is a tty master**, as the UART is a line whose driver is the
master of the tty it connects. Nothing about SSH enters the session or
the system domain beyond what a line already is:

* the SSH domain is a front end like the web domain: it parses the
  network's bytes and holds a login facet of the system domain and
  nothing that grants authority over principals;
* a login through the facet starts the principal's session from its
  template, as at the console, so the session's grants are the
  template's (S1), and the system domain introduces the session to the
  SSH domain, exporting the session's `erx_ssh_line`;
* a channel's shell runs on a tty of the session's relay whose master is
  the channel's process in the SSH domain, speaking the console
  interface's six messages, so line discipline, job control, `termios`,
  window size and hangup are the tty layer's, unchanged.

The consequences that would otherwise be special cases fall out:
`PermitRootLogin no` holds for the system shell by construction, since
only the console grants the system-shell facet, at a secure line, and an
SSH connection is never one; a connection's end is a hangup, which ends
its shells and its session; and a session started over SSH is
inspected, limited and ended as every session is.

### The SSH domain

The SSH domain is a configured `service` domain of the manifest, named
`ssh`, of the principal that owns the machine's services, on the BeamAsm
image by default. Its release ships `kernel`, `stdlib`, `erx`,
`erx_files`, `crypto`, `asn1`, `public_key`, `ssh` and `erx_ssh`,
erXos's application, which starts the daemon, provides its key callback
module `erx_ssh_keys`, its channel module `erx_ssh_cli` and its login
table.

Its manifest row holds:

* a `net` grant whose `ports` lists the SSH port (22, and 2222 in the
  QEMU manifests, where the harness forwards a host port to it), with
  `listen` on that port alone, `sockets` 80, the connection limit plus a
  margin, and `buffers` sized for them;
* the system domain's `erx_ssh_login` facet;
* at stage 4, the vault's key facet `{ssh_host, "ssh"}`;
* its arguments: the port, the methods offered (`publickey` and
  `keyboard-interactive`) and the limits below. The manifest check reads
  them, so the daemon has no configuration file and erXos adds no
  configuration parser.

The manifest check refuses an SSH domain row that holds any device, any
partition window, any other facet of the system domain, or an
`erx_ssh_login` facet on any other domain, so the domain that parses SSH
holds only its listener, its login facet and its host key's facet. The
system manifest lists the facet in the checked-in facet table with this
section as its justification.

`erx_ssh` starts the daemon with `ssh:daemon/3` on a socket listening
through the grant, as `gen_tcp` does in every domain
([design-network-stack.md](design-network-stack.md)), with the options of
[Algorithm policy](#algorithm-policy) and [Limits](#limits-and-who-pays),
`key_cb` set to `erx_ssh_keys`, `ssh_cli` set to `erx_ssh_cli`,
`pwdfun/4` calling the login facet, `parallel_login` true, `subsystems`
empty and `tcpip_tunnel_in` and `tcpip_tunnel_out` false. With
`parallel_login` true each accepted connection runs its key exchange and
authentication in a process of its own, so a client that stalls before
logging in holds only its own slot and never the acceptor. Each
connection is a process tree of the domain, so a malformed message ends
at most that connection.

### Host keys

The machine has one SSH host key, Ed25519, and offers only it.

* **With the vault** (stage 4), the key is a machine key in the vault's
  machine file, made by the vault at its first request after an
  installation, and the SSH domain holds the `{ssh_host, "ssh"}` key
  facet. `erx_ssh_keys:host_key/2` returns `{ok, {ssh2_pubkey, Blob}}` and
  `sign/3` asks the facet to sign the exchange hash
  ([design-system.md](design-system.md#the-vault)). The key's bytes never
  enter the SSH domain, so a compromise of the domain signs only while it
  lasts and steals nothing that outlives it. The login facet reads the
  key's public blob from the vault when it starts, and compares it with
  each key login's exchange ([Logging in](#logging-in)).
* **Before the vault** (stages 1 to 3, development builds only), the SSH
  domain keeps the key in its own directory on the data partition,
  `ssh_host_ed25519_key`, in OpenSSH's private key format, read and
  written with OTP's `ssh_file`. It makes the key when the file is
  missing; a file that does not decode stops the daemon with a log line
  naming the file, and nothing makes a new key in its place, because a
  host key that changes silently teaches users to accept the warning that
  guards against interception. Removing the file is how a developer asks
  for a new key. The release manifest check refuses an SSH domain without
  the host key facet, so this arrangement never reaches a release.

Either way the key persists across reboots and updates and changes only
at a fresh installation (S7). A key made on a boot whose `entropy_quality`
is weak, as every stopgap boot's is, is as guessable as that seed; the
daemon logs `host key made on a weak seed` once at each start while it
uses such a key, a residual recorded in `TODO.md`.

### Logging in

The daemon offers `publickey` and `keyboard-interactive`, FreeBSD's
default pair, and not `password`. Both reach the same facet.

**The login facet.** `erx_ssh_login` is a facet of the system domain,
declared in `abi/services/ssh.txt`, held by the SSH domain alone, with
five operations:

| Operation | Checks | Answer |
| --- | --- | --- |
| `cookie()` | none: the facet draws 16 bytes from `erx_bytes:entropy/1` and keeps them as an **outstanding cookie** for the login grace, 120 s; it keeps at most 128, and a new one beyond that drops the oldest | `{ok, Cookie}`, or `{error, unavailable}` when the generator fails |
| `key_ok(User, KeyBlob)` | `User` names an enrolled principal whose login keys hold `KeyBlob` | `true` or `false`, the same for an unknown principal and an unknown key |
| `login_key(User, Exchange, Alg, KeyBlob, Sig, Peer)` | as `key_ok`; `Alg` is `ssh-ed25519`; `Exchange` is the hash input of the connection's first key exchange, at most 64 KiB, which begins with five length-prefixed strings: the client's and the server's version lines, the client's and the server's `SSH_MSG_KEXINIT` payloads, and the host key. The server's payload begins with the byte `SSH_MSG_KEXINIT` and an outstanding cookie, and the host key is this machine's. The facet takes the SHA-256 of `Exchange` as the session identifier, builds the signed data of RFC 4252 section 7 itself from it, `User`, the service `ssh-connection`, `Alg` and `KeyBlob`, and checks the signature in `Sig`, the 83-byte signature blob of the name `ssh-ed25519` and 64 bytes, over that data with the system domain's Ed25519 verifier. A match retires the cookie | `{ok, Line}` or `{error, no_match \| limited \| unavailable}` |
| `login_passphrase(User, Passphrase, Peer)` | the principal service hands it to the vault, as `erx_web_login`'s `login` does, under the vault's limit for network connections, 5 failures in 60 s per name | `{ok, Line}` or `{error, no_match \| limited \| unavailable}` |
| `logout(Line)` | `Line` was started through this facet | `ok`; the session ends |

**A key login is bound to one fresh exchange with this machine.** The
construction: the facet chooses the cookie of the server's first
`SSH_MSG_KEXINIT` on each connection, and derives the session identifier
itself from that connection's first exchange. A client signs for a
session identifier only after it has checked the host key's signature
over the same hash, under a host key it accepts for the name it dialled
(RFC 4253, section 8). So when the input whose SHA-256 a client's
signature covers holds the facet's own outstanding cookie in the server's
`SSH_MSG_KEXINIT` and this machine's host key, that client completed,
after the facet chose the cookie, an exchange in which it accepted this
machine's host key. Each requirement follows:

* **Freshness.** A cookie the facet did not issue, one past its 120 s, or
  one a login has already used answers `no_match`. So neither a signature
  the principal made at another server nor a login the SSH domain watched
  here earlier, in this boot or a past one, opens a session. Across boots
  the facet's cookies, 128 bits from the kernel's generator, do not repeat
  while that generator is well seeded; on a weak seed, as on the stopgap,
  they are as guessable as the seed, a residual recorded in `TODO.md`.
* **Binding to this machine.** An exchange whose host key is another
  host's answers `no_match`, so a signature made for any other server,
  whoever chose its cookie, opens nothing here.
* **Nothing remembered.** The facet keeps only outstanding cookies, at
  most 128 of at most 120 s each, and drops the oldest first. Dropping one
  fails only the login in progress on its connection, so the table's
  bound, a restart of the facet and the SSH domain's end lose nothing a
  guarantee rests on, and no record of past logins grows with them.
* **One reading of the input.** The five strings are length-prefixed, so
  a byte string has one parse, and finding two different inputs with the
  same SHA-256 hash is computationally infeasible: the fields the facet
  checked are the fields the client hashed. The facet hashes the bytes
  it was given, unchanged, never a re-encoding of what it decoded. What
  follows the host key, the exchange values and the shared secret,
  differs between exchange methods and is hashed without being read, so
  the facet names no method.
* **One hash.** Every exchange the daemon offers hashes with SHA-256
  ([Algorithm policy](#algorithm-policy)), which the system domain
  computes with `erx_bytes:sha256/1`, a per-byte primitive of every
  runtime image ([design-runtime.md](design-runtime.md#per-byte-primitives)).

The cost is twofold: the exchange input carries the exchange's shared
secret into the system domain, which hashes it, never logs it and keeps
nothing of it; and the daemon offers neither NIST exchange whose hash is
SHA-384 or SHA-512, so the facet has one hash and no table from exchange
methods to hashes ([Algorithm policy](#algorithm-policy)). The facet's word is no stronger than the host key's:
while a compromised SSH domain runs, it can ask for cookies and have the
vault sign exchange hashes, so it can complete an exchange as this
machine with a client anywhere ([Security](#security)). OpenSSH's
privilege separation leaves its pre-authentication process the choice of
the session identifier, the first hash it asks the monitor to sign
([Context](#context)); this facet leaves the SSH domain no such choice.

Against the requirements:

* **S2.** The SSH domain supplies the parts of the signed data and the
  exchange's input, never the session identifier or the signed bytes, so
  it cannot make the facet check a signature made for another user,
  service, key, server or exchange. Without the principal's private key
  it starts a session only for a principal whose client completes an
  exchange with it, under this machine's host key, while it runs.
* **S3.** From the network, the system domain receives a key blob of 51
  bytes (the string `ssh-ed25519` and a 32-byte key), a signature blob of
  83 bytes (the same name and 64 bytes) and an exchange input of at most
  64 KiB, each decoded by one bounded Erlang decoder of the facet's,
  `erx_ssh_wire`, with a fuzz target. The decoder compares the fixed
  blobs whole against their one layout, and for each of the five strings
  checks its length against the bytes that remain before it takes the
  string; beyond its five strings the exchange input is only hashed. The
  decoder reads a key blob's 32 bytes only as bytes; the verifier decodes
  them as a point, under the rules below. Its Ed25519 verifier is the small
  verifier the update service uses ([design.md](design.md#decisions)),
  never OpenSSL. The vault receives from the network a user name, to look
  up that principal's login keys or passphrase slot, and a passphrase, for
  Argon2id, and from the SSH domain, through its host key facet, 32-byte
  exchange hashes to sign; it parses no SSH structure.
* **The method is decided by the facet, not the SSH domain.** OTP's daemon
  still checks the signature itself first; the facet's answer is the one
  that admits the connection.

**The verifier's acceptance rules.** The facet accepts a signature only
under RFC 8032's procedure, as RFC 8709 requires: `S` is below the group
order `L`; `R` and the public key decode as points under section 5.1.3,
with `y` below `p`, a square root that exists, and not `x = 0` with the
sign bit set; and the group equation holds, in either form section 5.1.7
allows. So a signature altered to `S + L`, which the equation alone would
accept, is refused. Those rules accept a public key of small order, a
point `P` for which `[8]P` is the neutral point, and anyone can make a
signature that such a key accepts, so `add_login_key` refuses a key that
does not decode or whose encoding is one of the eight points of small
order. The facet's tests call the verifier directly, not behind OTP's own
check, and the verifier is pinned at the security closure
([plan.md](plan.md#m11-security-closure)), before stage 4, only once
those tests pass on it ([Verification](#verification)).

**Login keys are Ed25519 only.** The daemon's `public_key` list is
`ssh-ed25519`, which serves both the host key and user authentication,
since OTP checks a user's algorithm against that list. A user with only
an RSA or ECDSA key logs in with the passphrase, or makes an Ed25519 key.

**Principals.** The SSH user name is the principal's name. A principal
that has not enrolled has no login keys and no passphrase slot, so it
gets `no_match`, the answer for a wrong key; app principals, which never
enrol, cannot log in. A session's limits, quotas and grants are its
template's, and a refused session start (the principal's domain quota
spent, its budget refused) answers `unavailable` and is logged with its
reason.

**What a login opens.** A passphrase login opens the principal's master
key in the vault, as at the console. A key login opens nothing. The
vault keeps a principal's keys open while any session of the principal
lives and destroys them when the last one ends
([design-system.md](design-system.md#the-vault)), so the session of a key
login can use the principal's keys exactly while another session of the
principal has them open, and keeps them open while it lives; when none
does, it has no keys, and a user who needs them logs in with the
passphrase. The keys belong to the principal, not to one of its
sessions, whichever way the session began. Keys open only to sessions
that gave the passphrase themselves would need the vault to record each
session's unlock; that record belongs to the merged login service
([Risks and open questions](#risks-and-open-questions)).

**OTP's hooks.** When the key callback module exports them, the daemon
asks `kex_cookie/1` for the cookie of each connection's first
`SSH_MSG_KEXINIT`, keeps that exchange's hash input until authentication
succeeds, and has `ssh_auth:verify_sig/7` call `verify_user/6` with it
and the 83-byte signature blob after its own checks
([Edits to OTP's ssh](#edits-to-otps-ssh)).
`erx_ssh_keys:kex_cookie/1` calls `cookie`, and a connection whose cookie
the facet refuses closes before its exchange; `verify_user/6` calls
`login_key` and stores `{ok, Line}` in the login table under the
connection's process; `is_auth_key/3` calls `key_ok`; `pwdfun/4` calls
`login_passphrase` and stores the line the same way. A connection whose
table row is missing when a channel asks for its line has not logged in
through the facet and is closed.

### Login keys

Each principal's login keys are a list of Ed25519 public keys kept by the
vault, in the principal's own file, in a section sealed under a key
derived from the machine's master key and the principal's name, so the
vault reads them at any time without the principal's passphrase, nothing
that writes the medium under the `device` or `tpm` backend can add one,
and they go with the file when it is removed
([design-system.md](design-system.md#the-vault)).

* **Adding a key needs the passphrase**, as changing it does: the
  session's `sshkeys add FILE` command reads an OpenSSH public key line
  with OTP's `ssh_file:decode/2` in the session, asks for the passphrase
  at its tty, and sends the key's blob and the passphrase through the
  session's credentials facet of the principal service to the vault,
  which checks the passphrase and publishes the file through its owner.
  The principal service refuses a blob that `erx_ssh_wire` does not
  decode or whose key is of small order
  ([Logging in](#logging-in)). A session left open, or a program in it,
  cannot add a way in on its own.
* **Removing a key** (`sshkeys del FINGERPRINT`) and listing them
  (`sshkeys`, printing each key in `authorized_keys` format with its
  SHA-256 fingerprint) need no passphrase, since they add no authority.
* **The first key** is added from a session of a passphrase login, at the
  console or over SSH, so presence at the machine stays the root of
  trust for enrolment.

There is no `~/.ssh/authorized_keys`: a file the principals' storage
domain serves, which every program of the session can write, would let
anyone who writes the data partition, or anything running in the
session, add a login. `~/.ssh/known_hosts` and `~/.ssh/config` stay
ordinary files of the principal, used by clients as on FreeBSD.

**Before the vault** (stages 2 and 3, development builds only), `root`
has one login key: the public half of a development key that `make setup`
makes in the build tree, which the boot image carries as the development
signing key is carried. `tools/erx ssh` runs the host's `ssh` with that
key and the guest's forwarded port. The facet accepts it for `root`
alone. It issues cookies and derives each login's session identifier as
at stage 4, but until the system domain has its Ed25519 verifier and the
vault the host key, it compares no host key and accepts `login_key` on
the SSH domain's own signature check, a development-build residual
recorded in `TODO.md`. `login_passphrase` answers `unavailable`, since no
passphrase exists.

### Sessions, ttys and shells

`erx_ssh_line` is the session's process that the SSH domain reaches,
exported to it at the introduction, as `erx_web_line` is to the web
domain. It takes two requests, each from a channel process of the SSH
domain, heard through that domain's envelope, and answers each `ok` or
`{error, limited | badarg}`:

* **`{open_tty, Channel, Run, Term, Rows, Columns}`** for a channel that
  asked for a pseudo-terminal and then a shell or a command. The relay
  makes a tty whose master is `Channel` and starts the principal's shell
  on it. From then on the tty and the channel exchange the six console
  messages, with `window-change` sent as `tty_size` and the channel's end
  or the connection's as `tty_hangup`. The shell's `TERM` is `Term` when
  `abi/termcap` names it and `vt100` otherwise; a size of zero, which
  `pty-req` allows, is taken as 24 rows or 80 columns.
* **`{open_job, Channel, Run}`** for a channel with no pseudo-terminal.
  The session starts the shell with standard input, output and error on
  three pipes of its pipe server ([design-pipes.md](design-pipes.md)),
  whose other ends the line holds, since a pipe end never leaves the
  session, as a command domain's stream relay holds its command's
  ([design-programs.md](design-programs.md#what-a-program-can-start)).
  The line relays them to the channel with the job messages below, so a
  program's error output stays apart from its output, as `git` and
  `rsync` over SSH need.

`Run` says what runs: `shell` runs `rc`, interactive on a tty and reading
commands from standard input in a job, as OpenSSH runs the user's shell
without a tty; `{exec, Command}` runs `rc -c Command`, for an `exec`
request, with `Command` a binary of 1 to 32 KiB holding no NUL byte. A
line answers `limited` past ten open channels, `max_channels`, and
`badarg` to any other shape.

A job's channel and its line exchange seven closed messages, heard
through each other's domain envelope and each checked by its receiver:

| Message | Direction | The receiver's check | If it fails |
| --- | --- | --- | --- |
| `{job_input, Bytes}` | channel to line | a binary of at most 32 KiB, the channel's packet size, with no other `job_input` unanswered; the line writes it to standard input's pipe, waiting for room | the line ends the job, as at `job_hangup` |
| `job_written` | line to channel | a `job_input` is unanswered; the channel then opens the client's window by its size | the channel closes |
| `job_eof` | channel to line | none; the line closes standard input's writing end once what came before it is written, and the job's output and status still flow | not applicable |
| `{job_output, Stream, Bytes}` | line to channel | `Stream` is `stdout` or `stderr`, `Bytes` a binary of at most 32 KiB, with no other `job_output` unanswered; the channel sends it as channel data or extended data within the client's window | the channel closes |
| `job_sent` | channel to line | a `job_output` is unanswered; the line then reads the pipes again | ignored, as a late repeat |
| `job_hangup` | channel to line | that atom; it holds from then on | not applicable; the line closes every end and ends the job's programs, as the relay ends a tty's shells at `tty_hangup` |
| `{exited, Status}` | line to channel | `Status` is an integer from 0 to 255 | the channel closes |

`{exited, Status}` serves ttys too: the line sends it once what it
started on the channel, the shell on the tty or the job, has ended and
its last output has been taken, by `tty_taken` or `job_sent`, so it
arrives after every byte of output. The channel then sends SSH's
`exit-status`, its end of file and its close, and sends `tty_hangup` to
a tty. One unanswered message each way bounds what either side holds for
a channel to 32 KiB of input and 32 KiB of output beyond the client's own
window, and a pipe's writer that waits for room carries back-pressure to
the client's window.

Input flows into a tty as `tty_input` messages of at most 4 KiB; the tty
bounds what waits unread, and the channel adjusts the SSH window only as
it sends, so a client that types faster than the program reads loses the
excess as on a line's overrun ([design-live.md](design-live.md#paths)).

At the end of the connection every channel's tty gets `tty_hangup` and
every job's line `job_hangup`; the SSH domain then calls `logout(Line)`,
and the session ends as a console session ends at log-out. If the SSH
domain ends first, the facet ends with it and every session its logins
started ends, as the web's do.

### Channel policy

| Request | Answer | Reason |
| --- | --- | --- |
| `session` channel; `pty-req`, `shell`, `exec`, `window-change` | served, as above | |
| `env` | ignored | FreeBSD's `sshd_config` accepts no variable; `TERM` comes with `pty-req` |
| `subsystem` (`sftp`) | refused | OTP's `ssh_sftpd` would run in the SSH domain, on that domain's files, not the principal's |
| `direct-tcpip`, `tcpip-forward`, `direct-streamlocal@openssh.com` | refused, administratively prohibited | a forwarded connection would use the SSH domain's `net` grant, not the principal's |
| `auth-agent-req@openssh.com`, `x11-req` | refused | |
| `signal`, `break` | ignored | the tty's `Ctrl-C` is the interrupt |

SFTP and forwarding are planned features, recorded in `TODO.md`; their
design runs them in the session, as `open_job` runs a command, so they
use the session's namespace and its own `net` grant, never the SSH
domain's.

### Algorithm policy

The daemon's `preferred_algorithms` follow FreeBSD's server lists, in
FreeBSD's order, less what OTP does not implement and the exchanges whose
hash is not SHA-256:

| Class | Offered |
| --- | --- |
| key exchange | `mlkem768x25519-sha256`, `curve25519-sha256`, `curve25519-sha256@libssh.org`, `ecdh-sha2-nistp256` |
| host key and user key | `ssh-ed25519` |
| cipher | `chacha20-poly1305@openssh.com`, `aes128-gcm@openssh.com`, `aes256-gcm@openssh.com`, `aes128-ctr`, `aes192-ctr`, `aes256-ctr` |
| MAC | `hmac-sha2-256-etm@openssh.com`, `hmac-sha2-512-etm@openssh.com`, `hmac-sha1-etm@openssh.com`, `hmac-sha2-256`, `hmac-sha2-512`, `hmac-sha1` |
| compression | `none` |

OTP has neither `sntrup761x25519-sha512` nor the UMAC family. Every
exchange offered hashes with SHA-256 in OTP (`sha/1`,
`ssh_transport.erl:2395-2416`), so the login facet has one hash
([Logging in](#logging-in)). The server offers neither
`ecdh-sha2-nistp384` nor `ecdh-sha2-nistp521`, which hash with SHA-384
and SHA-512: the facet would then need SHA-384 and SHA-512 exposed to
it, a choice of hash by exchange method, and tests of each. Neither
hash is a new implementation in the system domain, since the Ed25519
verifier computes SHA-512 (RFC 8032, section 5.1.7) and SHA-384 is
SHA-512's processing with other initial values and a shorter output
(RFC 6234, section 6.4); what the narrower list saves is that method
table and its tests. A client with FreeBSD's default list offers the
two only after `mlkem768x25519-sha256`, the Curve25519 exchanges and
`ecdh-sha2-nistp256` (`KEX_CLIENT_KEX`, `myproposal.h:37-41`), so it
never needs them here. The host key list is narrower
than FreeBSD's because the machine has one Ed25519 key. Compression is
off, so no compressed length reveals anything of the plaintext. The lists
are fixed by the release, so no client can negotiate below them (S6).
The strict key exchange is offered and used with every client that
offers it too; a client that does not offer it connects without it, and
its connection is open to the prefix truncation that strict exchange
closes, which the log record of each connection shows.

### Limits and who pays

| Limit | Value | Bounds | Paid by |
| --- | --- | --- | --- |
| connections at once (`max_sessions`) | 64 | the SSH domain's memory and sockets | the SSH domain's budget and grant |
| logins in progress (`parallel_login`) | true: one process per connection | a stalled connection holds its own slot, never the acceptor | the SSH domain |
| login grace (`negotiation_timeout`) | 120 s, FreeBSD's `LoginGraceTime` | how long an unauthenticated connection holds a slot | the SSH domain |
| version line (`hello_timeout`) | 30 s | idle connections before the version line | the SSH domain |
| authentication attempts per connection (`max_auth_tries`) | 6, FreeBSD's `MaxAuthTries` | guesses per connection | the SSH domain |
| outstanding cookies | 128, each for 120 s, the oldest dropped first | the login facet's memory | the system domain, bounded by the table |
| failed logins per name | the vault's 5 in 60 s from network connections | guessing across connections | the vault, on its own grant |
| channels per connection (`max_channels`) | 10, FreeBSD's `MaxSessions` | ttys and jobs per connection | the session, for each tty or job |
| a channel's receive window and packet | 64 KiB and 32 KiB | what the SSH domain holds for one channel | the SSH domain |
| a job's messages in flight | one each way, 32 KiB each | what the line and the channel hold beyond the window | the session and the SSH domain |
| sessions per principal | the principal's domain quota | session domains | the principal's budget |

The SSH domain's worst case is 64 connections of 10 channels each
holding a full window, 40 MiB, within its own budget, so no client makes
it take memory from anyone else. FreeBSD's random early drop of
unauthenticated connections (`MaxStartups`) has no OTP counterpart: a
flood of unauthenticated connections fills the 64 slots until their
grace ends, refusing others, and a flood of short ones can drop a
waiting login's cookie, so that login fails and its client may try
again; both fail safe and are recorded as a residual in `TODO.md`.

### Logging

Every connection, authentication result and session start or end is a
structured log record of the SSH domain: the peer's address and port,
the client's version string, the user name, the method, the key's
SHA-256 fingerprint, whether the strict key exchange was negotiated and
the outcome. The version string and the user name are the network's
text, so they are record fields that only the log sink's escaper
renders, with tab and newline escaped, as for any text attributed to a
source (S4). OTP's own `ssh` log lines go through the same handler,
`erx_log_h`, with `max_log_item_len` bounding what they quote. The
principal service logs each session the facet starts, under the system
domain's name, which is the record of who logged in, with the SSH
domain's claimed peer marked as its claim, and each login key added or
removed, with its fingerprint and the line of the session that asked.
No record carries a passphrase, an exchange input or a session
identifier.

## Invariants

| Invariant | Holds because |
| --- | --- |
| **H1.** A session started over SSH holds its template's facets and nothing else | the domain service makes it from the template; the facet chooses only the start map |
| **H2.** No session starts without a check outside the SSH domain | `erx_ssh_login` is the SSH domain's only way to a session, and it decides from the vault or the verifier |
| **H3.** The SSH domain holds no authority over principals | the manifest check limits its row to its grant, the login facet and the host key facet |
| **H4.** A connection's end ends what it started | `tty_hangup` and `job_hangup` end its shells and jobs; `logout` ends its session; the facet's end ends all of them |
| **H5.** The system domain runs no OpenSSL; neither it nor the vault parses an SSH packet, and the vault decodes no SSH structure | the facet's decoder compares two fixed-format blobs against their one layout and takes five length-prefixed strings, each checked against the bytes that remain, in Erlang; the facet hashes the input as given with `erx_bytes:sha256/1` and checks Ed25519 with the update verifier, which alone decodes a key's bytes as a point; the vault sees lookups, passphrases, 32-byte exchange hashes and key blobs the principal service has already decoded |
| **H6.** The host key never changes silently | it is made only when absent, and a corrupt one stops the daemon |
| **H7.** A key login names one exchange that began after the facet chose its cookie and that carried this machine's host key | the facet derives the session identifier from the exchange input itself, finds its own outstanding cookie and the host key in that input, and retires the cookie at the login |

## Failure handling

| Failure | Seen as | Result |
| --- | --- | --- |
| a connection's process crashes on a malformed message | its exit | that connection closes; its ttys hang up, its jobs end and its session ends |
| the SSH domain crashes | its exit record | every connection closes and every session its logins started ends; the facet and its cookies end with it; the domain service restarts it under its restart intensity and it listens again |
| the facet's `cookie` answers `unavailable` (the kernel's generator fails) | `kex_cookie/1` raises | that connection closes before its key exchange, with one log line; others go on |
| a cookie dropped as the oldest, or past its grace | `login_key` finds it not outstanding | that key login answers `no_match`; the client may try its passphrase or connect again |
| the host key file is missing (before the vault) | `ssh_file` finds none | a new key is made and logged with its fingerprint |
| the host key file does not decode (before the vault) | `ssh_file`'s error | the daemon does not listen; one log line names the file; the domain stays up |
| the vault answers `unavailable` (its partition or backend down) | the host key facet's or login's answer | the daemon waits, retrying every 10 s with one log line, and does not listen until the host key answers; logins answer `unavailable` |
| the network domain restarts | the grant's sockets close | the listener and every connection end; `erx_ssh` listens again when the grant answers |
| a session cannot start (quota, budget) | the domain service's refusal | the login answers `unavailable`, logged with the reason; the client sees authentication fail |
| entropy unavailable in the SSH domain | `crypto` raises in the key exchange | that connection closes ([design-crypto.md](design-crypto.md#seeding)) |

## Refusals and error results

The client sees SSH's own results: a refused method or a `no_match` is
`SSH_MSG_USERAUTH_FAILURE`; `limited` and `unavailable` are failures too,
logged with their reason, so a client learns nothing more than a wrong
key; past `max_auth_tries` the connection is disconnected; a refused
channel request, a line's `limited` or `badarg` included, is
`SSH_MSG_CHANNEL_FAILURE`, and a refused channel type
`SSH_MSG_CHANNEL_OPEN_FAILURE` with `SSH_OPEN_ADMINISTRATIVELY_PROHIBITED`;
an algorithm mismatch ends the key exchange. The facet's answers are the
closed sets of its table, and `erx_ssh_wire` refuses a blob of any other
length or name, and an exchange input over 64 KiB, short of its five
strings or with a string longer than what remains, with `badarg`, which
the facet answers `no_match`.

## Security

**Threats.**

* **A network attacker** reaches the SSH domain's Erlang protocol code
  and, through `crypto`, OpenSSL's key exchange and signature code. The
  protocol's parsers are Erlang, so a malformed message ends a connection
  process; a memory error in OpenSSL or the `crypto` NIF takes the whole
  SSH domain. It reaches the system domain only through the login
  facet's five operations and their bounded inputs, and the vault
  only with a user name and a passphrase.
* **A compromised SSH domain** sees the plaintext of every live SSH
  connection and can type into every tty it masters, so it acts as each
  principal logged in through it while that login lasts, as the web
  domain can for its lines. It can sign as the host while it runs, and so
  complete an exchange as this machine with any client that accepts this
  machine's host key, whether the client dialled this machine or a server
  that relays the client's connection here: a client that trusts the key
  for this machine's name, or that accepts it on first use for a name it
  has not seen. Such a client's login is a login through it, as with any
  server whose host key an attacker holds.
  It cannot start a session for a principal whose client makes no
  exchange with it while it runs: a signature made at another server, or
  for an exchange whose cookie is spent, expired or not the facet's,
  opens nothing ([Logging in](#logging-in)). It cannot read any key, or
  reach any principal's files except through a shell it can type into.
* **Credentials typed through the SSH domain outlive its compromise.** A
  compromised SSH domain reads every passphrase given through it, at
  `keyboard-interactive` and at every tty it masters, where `sshkeys add`
  asks for one. With a passphrase it can log in as that principal later,
  and it can type `sshkeys add` with a key of its own into a session's
  tty. Restarting the SSH domain from its image ends neither. Keeping
  private keys in the vault does not prevent this: the passphrase and the
  login keys are the principal's way in, not keys the vault uses. The
  principal recovers by changing the passphrase from a session the SSH
  domain does not carry, at the console, and by listing the login keys
  with `sshkeys` and removing those it did not add; the principal
  service's log names each addition with its fingerprint and line
  ([Logging](#logging)).
* **A compromised session domain** holds its own line and its ttys; it
  cannot add a login key without the passphrase or reach another
  principal's session.
* **A stolen login key** logs in as its principal, and its session uses
  the principal's vault keys while another session holds them open
  ([Logging in](#logging-in)); `sshkeys del` refuses it every later
  login, and a session it started runs until it ends.
* **Key theft.** The host key and every private key are the vault's
  (stage 4), and the login keys are public. Before the vault the host key
  is a file of the SSH domain's directory, readable by whoever reads the
  data partition, in development builds only.
* **Downgrade.** The lists are fixed and no SHA-1 signature, CBC cipher or
  finite-field group is offered. The strict key exchange holds for every
  client that offers it; a client that does not is exposed to the prefix
  truncation it closes, and its log record says so.
* **Timing.** The key exchange, ciphers and the host key's signing are
  OpenSSL's constant-time code
  ([design-crypto.md](design-crypto.md#cpu-features-and-constant-time)).
  The facet's work is on public data, the exchange's shared secret aside,
  which it only hashes. `key_ok` answers the same for an unknown
  principal as for an unknown key; its timing is not equalized, and
  principals' names are not secret, since the manifest lists them.

**What OpenSSL's code can reach** in the SSH domain is that domain: its
memory, which holds every connection's session keys and data, its
grant's sockets, its login facet and its host key facet. No mapping is
writable and executable, and OpenSSL makes no code.

## Alternatives considered

* **The daemon in the system domain.** Rejected: it would put OpenSSL and
  a network parser into the trusted base, against the existing decision.
* **The daemon in the network domain.** Rejected: that domain parses
  every packet and calls no OpenSSL
  ([design-crypto.md](design-crypto.md#domains-that-call-no-openssl)).
* **A domain per connection**, as OpenSSH separates each connection's
  process. Rejected for now: each login already gets its own session
  domain, so a compromise from one connection reaches other principals
  only through a memory error in the SSH domain's OpenSSL or NIF, and the
  protocol parsing itself is Erlang; a domain per connection would cost a
  runtime per connection and a way to hand an accepted socket and its
  key exchange to another domain, which nothing provides.
* **The SSH transport moving into the session after login.** Rejected:
  OTP's connection state cannot be handed between domains, and the
  pre-login half would still need the SSH domain.
* **The session identifier on the SSH domain's word, refused when seen
  before.** Rejected: a signature the principal made at any other server,
  for an identifier never seen here, would open a session, and the record
  of identifiers seen grows with every login and must outlive the facet's
  restarts.
* **OpenSSH's monitor rule**, the session identifier as the first hash
  the host key signs for the connection (`monitor.c:767-772`). Rejected:
  the SSH domain would still choose that hash, as the monitor's own
  comment says (`:739-741`).
* **The vault deriving the session identifier**: its host key facet
  issuing the cookie and checking the exchange input against its own key
  before it signs, and the login facet accepting only an identifier the
  vault signed. Not adopted: it is the same check, in the domain that
  holds every logged-in principal's keys, with each exchange input hashed
  there, and it makes every key login a question to the vault. What it
  adds, a host key that signs only exchanges begun with its own cookie,
  does not limit a compromised SSH domain, which can ask for cookies.
* **`ecdh-sha2-nistp384` and `ecdh-sha2-nistp521` offered**, with
  SHA-384 and SHA-512 exposed to the login facet. Not adopted: the
  Ed25519 verifier already computes SHA-512, and SHA-384 is its
  processing with other initial values, so the cost is not new hash code
  but a choice of hash by exchange method in the facet and the tests of
  each, for exchanges a client with FreeBSD's default list never needs,
  since it offers the Curve25519 exchanges and `ecdh-sha2-nistp256`
  before them ([Algorithm policy](#algorithm-policy)).
* **Signatures checked in the vault with OpenSSL**, which would admit RSA
  and ECDSA login keys. Rejected: it would put network bytes into the
  domain that holds every logged-in principal's keys.
* **`~/.ssh/authorized_keys` on the data partition**, FreeBSD's default.
  Rejected: whoever writes the data partition or runs in the session
  could add a login, which the vault's design refuses for every other
  credential.
* **The daemon's word for who logged in.** Rejected: a compromise of the
  SSH domain would be a login as anyone.
* **Dropping the SHA-1 MACs.** Not adopted: FreeBSD offers them, after
  the SHA-2 ones, and the AEAD ciphers that come first use no MAC.

## Risks and open questions

* **One login service for front ends.** `erx_ssh_login` and
  `erx_web_login` have the same shape, and they merge into one login
  service, whose grant names the front end's line, when login is designed
  once for every place a person meets the system
  ([design-web.md](design-web.md#risks-and-open-questions)); until then
  they are two facets. That service is also where a per-session unlock
  record belongs, should a principal's keys open only to the sessions
  that gave its passphrase themselves, with a way to give the passphrase
  in a session after a key login; the item is in `TODO.md`.
* **Ed25519-only login keys**, for S3: RSA and ECDSA users use the
  passphrase method or make an Ed25519 key. FIDO keys
  (`sk-ssh-ed25519@openssh.com`) are not accepted, a planned feature in
  `TODO.md`.
* **Passphrases over SSH** are on, as FreeBSD's keyboard-interactive is,
  under the vault's network limit; a manifest argument turns the method
  off.
* **Typed-ahead input is lost past the tty's bound**, as at the console;
  a paste larger than the bound into a program that is not reading loses
  bytes. An acknowledgement of input in the console interface would carry
  the SSH window to the tty; recorded in `TODO.md`.
* **Session creation per login** costs a domain's start; the latency of
  an SSH login is on the watch list
  ([todo-performance.md](todo-performance.md)),
  settled by `tools/erx bench ssh-login`.
