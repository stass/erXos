# SSH

A person on another machine runs `ssh root@erxos` and gets a shell in a
session of their principal, holding exactly that session's grants, as a
login at the console gives. OTP's `ssh` daemon serves the protocol in a
configured domain of its own, the **SSH domain**, which parses what the
network sends; the system domain decides who logs in; the vault holds the
host key and each principal's login keys; and the shell runs in the
principal's session, on a tty whose master is the SSH channel. The
cryptography underneath is [design-crypto.md](design-crypto.md).

## Context

The roadmap puts SSH in M14, over erXos's own TCP/IP stack on QEMU in
1b-G, then on the boards ([plan.md](plan.md#1b-g-networking-on-qemu)),
with the host key signed by the vault's key facet at M12's keys
([plan.md](plan.md#m12-storage-networking-boards)). It rests on
principals and the sessions a login starts from a session template alone
([design-domains.md](design-domains.md#principals-sessions-and-quotas));
the web domain's login, the precedent for a configured domain that
parses untrusted bytes and asks the system domain to start a session
([design-web.md](design-web.md#logging-in-and-the-line)); ttys, whose
master in another domain speaks seven closed messages through its
domain's envelope and whose `tty_hangup` ends the tty's shells
([design-live.md](design-live.md#paths)); pipes, whose ends stay in the
session ([design-programs.md](design-programs.md#what-a-program-can-start),
[design-pipes.md](design-pipes.md#the-sessions-pipe-nif)); the vault,
whose `{ssh_host, Name}` facet signs exchange hashes and never gives the
key away, and which keeps a principal's opened keys while a session of
it lives ([design-system.md](design-system.md#the-vault)); and the
network grant, which lists the ports a domain may bind, ports below
1,024 only when listed
([design-network-stack.md](design-network-stack.md)).

What the sources say, read at the pins of [Sources](#sources):

* **The session identifier is the first exchange's hash.** The exchange
  hash is `HASH(V_C || V_S || I_C || I_S || K_S || e || f || K)`: both
  sides' version lines, both sides' `SSH_MSG_KEXINIT` payloads, the
  server's host key, both exchange values and the shared secret, each
  length-prefixed (RFC 4253, section 8). The hash of the first exchange is
  the session identifier and never changes (section 7.2). Every
  `SSH_MSG_KEXINIT` begins with a 16-byte cookie that "MUST be a random
  value generated by the sender" (section 7.1). The client checks that
  `K_S` is the host key for the server it dialled and verifies the host
  key's signature over the hash before it goes on (section 8, step 3). A
  `publickey` signature covers the session identifier, the message
  number, the user, the service, the method, `TRUE`, the algorithm and the
  key, and nothing else of the server's (RFC 4252, section 7).
* **OTP builds that input and keeps its hash, not the input.** The server builds
  the hash input in `kex_plaintext/3`, five strings followed by what the
  exchange method adds (`lib/ssh/src/ssh_transport.erl:2318-2323`); for
  the ECDH and Curve25519 methods that is `Q_C` and `Q_S` as strings and
  `K` as an mpint (`:2332-2334`), for `mlkem768x25519-sha256` `C_INIT`
  and `S_REPLY` as strings and `K` already encoded (`:2325-2331`). The
  server keeps the hash and the encoded `K` and drops the rest
  (`:905-907`, `:988-990`). Its
  cookie is `ssh_bits:random(16)` (`:353`). `verify_sig/7` builds the
  signed data of RFC 4252 section 7 from the stored session identifier
  (`lib/ssh/src/ssh_auth.erl:583-592`).
* **OTP 29.1.2's daemon serves nothing by default**: `subsystems`
  defaults to `[]`, `shell` and `exec` to `disabled`, `tcpip_tunnel_in`
  and `tcpip_tunnel_out` to `false` (`lib/ssh/src/ssh_options.erl`,
  `default(server)`, `:419`, `:465`, `:471`); `max_sessions` is 1,024,
  `max_channels` 256, `parallel_login` false, `negotiation_timeout` 120 s
  and `hello_timeout` 30 s (`:584-612`). With `parallel_login` false, the
  acceptor starts each connection in its own loop and waits for that
  connection's authentication, up to `negotiation_timeout`, before it
  accepts the next (`ssh_acceptor.erl:108-111`, `ssh_system_sup.erl:127`,
  `ssh_connection_handler.erl:124-140`, `:495-513`). It has no option
  bounding the authentication attempts of one connection. A channel's
  receive window is the connection socket's receive buffer as the
  system reports it, after the handler asks for at least 640 KiB and
  takes whatever it gets, and its packet is that
  buffer's user-level size, at most 64 KiB
  (`init_inet_buffers_window/1` and `update_inet_buffers/1` in
  `ssh_connection_handler.erl`); `ssh_connect.hrl:27-28`'s ten packets
  of 64 KiB is only the default when the socket names none. No option
  sets either. A channel process of `ssh_server_channel` opens the
  peer's window again by the size of every data message once its
  callback has taken it (`handle_info/2` and `adjust_window/1` in
  `ssh_client_channel.erl`), whatever the callback did with the data,
  and data past the window is taken (`channel_data_reply_msg/4` in
  `ssh_connection.erl`).
* **OTP checks a public key in the daemon's own process**:
  `ssh_auth:verify_sig/7` asks the key callback's `is_auth_key/3`, builds
  the signed data and verifies it there, with the algorithm required to
  be in the daemon's `preferred_algorithms` (`ssh_auth.erl:565-581`). The
  daemon reads its host key through `host_key/2`
  (`lib/ssh/src/ssh_server_key_api.erl:61`, `ssh_transport.erl:1111`).
  A terminating connection's status report omits the key exchange's
  secrets by a list of `#ssh{}` fields in `clean/1`
  (`ssh_connection_handler.erl:1604-1605`, `:1616-1635`); a normal one,
  as `sys:get_status/1` asks for, returns the state unchanged (`:1602-1603`).
  Each connection's handler keeps the first exchange's hash as the
  session identifier and never replaces it at a rekeying (`sid/2`,
  `ssh_transport.erl:1105-1106`). User authentication succeeds for every
  method through one function, `connected_state/5`
  (`ssh_fsm_userauth_server.erl:173-181`). `verify_sig/7` takes the
  signature field apart into the signature blob, `AlgSig`, which holds the
  algorithm name and the signature, and the bare signature inside it
  (`ssh_auth.erl:574-576`).
* **OTP negotiates the strict key exchange** that closes the Terrapin
  prefix truncation when both sides offer it, and connects a peer that
  does not offer it without it (`ssh_transport.erl:311`, `:538-550`); it
  sends `server-sig-algs` (`:1068`, `:1095`).
* **OpenSSH's privilege separation** takes the session identifier from
  the first hash its host key signs for a connection
  (`crypto/openssh/monitor.c:767-772`) and checks a user's signed data
  against it (`:1366-1393`); its own comment says it cannot check the
  exchange behind the hash, "since what is signed is the hash, rather
  than the full kex structure" (`:739-741`).
* **Ed25519 verification** is RFC 8032's (RFC 8709, section 7): `S` lies
  in `0 <= S < L`, `R` and the public key decode as points, which fails
  when `y >= p`, when no square root exists, or when `x = 0` with its sign
  bit set, and the group equation holds, with or without the cofactor
  (RFC 8032, sections 5.1.3 and 5.1.7).
* **FreeBSD's sshd** (OpenSSH 10.0, `FreeBSD-20250801`, in
  `crypto/openssh/`): its server key exchanges are
  `mlkem768x25519-sha256`, `sntrup761x25519-sha512` in two names,
  `curve25519-sha256` in two names and `ecdh-sha2-nistp256`, `-384`,
  `-521`, with no finite-field group (`myproposal.h:27-35`); its ciphers
  `chacha20-poly1305@openssh.com`, `aes128-gcm@openssh.com`,
  `aes256-gcm@openssh.com` and `aes128-ctr`, `aes192-ctr`, `aes256-ctr`
  (`:61-64`); its MACs the UMAC and HMAC-SHA-2 and HMAC-SHA-1 families,
  `-etm` first (`:68-78`); its user key algorithms Ed25519, ECDSA and
  `rsa-sha2-512`, `rsa-sha2-256`, no `ssh-rsa` (`:43-59`). Its defaults:
  `LoginGraceTime` 120, `PermitRootLogin no`, `PasswordAuthentication no`
  with `KbdInteractiveAuthentication yes` through PAM,
  `MaxStartups 10:30:100`, `X11Forwarding no`, `PermitTunnel no`,
  `AllowTcpForwarding` and agent forwarding allowed
  (`servconf.c:300-480`), `MaxAuthTries` 6 and `MaxSessions` 10
  (`servconf.h:39-40`); its `sshd_config` sets
  `AuthorizedKeysFile .ssh/authorized_keys` and the `sftp` subsystem
  (`sshd_config:44`, `:117`). Every user authentication request that
  fails counts against `MaxAuthTries`, a `none` request too, except a
  `none` request that is the connection's first, and the failure that
  brings the count to `MaxAuthTries` is answered with a disconnect
  instead of `SSH_MSG_USERAUTH_FAILURE` (`auth2.c:442-452`); a request
  for a method it does not offer fails and counts (`:342-352`).

## Requirements

* **S1.** A login gets exactly its principal's session: the session's
  facets are its template's, and nothing of the SSH domain's authority
  passes to it.
* **S2.** The SSH domain cannot start a session on its own word: who
  logs in is decided outside it, from a passphrase the vault checks, or
  from a signature by one of the principal's login keys over a session
  identifier that the deciding side derives itself, from an exchange that
  carried a cookie the deciding side chose and this machine's host key.
* **S3.** The system domain never runs OpenSSL, and neither it nor the
  vault parses an SSH packet: what reaches them from the network is a few
  bounded values, each of one purpose, and the system domain's one decoder
  of them reads only fixed-format Ed25519 key and signature blobs and the
  five length-prefixed strings that begin an exchange's hash input; the
  vault decodes no SSH structure at all ([Logging in](#logging-in)).
* **S4.** Text from the network reaches a log only through the log
  sink's escaper.
* **S5.** What a connection can make the machine spend is bounded, and
  charged to the SSH domain or to the principal's session.
* **S6.** The algorithms offered are fixed by configuration, with no
  SHA-1 signature, CBC cipher or finite-field exchange.
* **S7.** Clients see one host key per installation, the same across
  reboots and updates.

## Design

### An SSH connection is a line

The construction: **an SSH connection is a login line, and each of its
channels is a tty master**, as the UART is a line whose driver is the
master of the tty it connects. Nothing about SSH enters the session or
the system domain beyond what a line already is:

* the SSH domain is a front end like the web domain: it parses the
  network's bytes and holds a login facet of the system domain and
  nothing that grants authority over principals;
* a login through the facet starts the principal's session from its
  template, as at the console, so the session's grants are the
  template's (S1), and the system domain has the session mint its
  line, the `tty_line` facet in front of `erx_tty_line`, for the SSH
  domain ([design-system.md](design-system.md#a-sessions-lines));
* a channel's shell runs on a tty of the session's relay whose master is
  the channel's process in the SSH domain, speaking the console
  interface's seven messages, so line discipline, job control, `termios`,
  window size and hangup are the tty layer's, unchanged.

The consequences that would otherwise be special cases fall out:
`PermitRootLogin no` holds for the system shell by construction, since
only the console grants the system-shell facet, at a secure line, and an
SSH connection is never one; a connection's end is a hangup, which ends
its shells and its session; and a session started over SSH is
inspected, limited and ended as every session is.

### The SSH domain

The SSH domain is a configured `service` domain of the manifest, named
`ssh`, of the principal that owns the machine's services, on the BeamAsm
image by default. Its release ships `kernel`, `stdlib`, `erx`,
`erx_files`, `crypto`, `asn1`, `public_key`, `ssh` and `erx_ssh`,
erXos's application, which starts the daemon, provides its key callback
module `erx_ssh_keys`, its channel module `erx_ssh_cli` and its login
table.

Its manifest row holds:

* a `net` grant whose `ports` lists the SSH port (22, and 2222 in the
  QEMU manifests, where the harness forwards a host port to it), with
  `listen` on that port alone, `sockets` 80, the connection limit plus a
  margin, and `buffers` sized for them;
* the system domain's `login` facet, with `line` `tty_line` and the
  operations of [design-login.md](design-login.md#who-holds-it)'s table;
* before the vault, a read-write grant of the `ssh_state` files service,
  the host key's directory ([Host keys](#host-keys)), and at stage 4 the
  vault's key facet `{ssh_host, "ssh"}` in its place;
* its arguments: the port, the methods offered (`publickey` and
  `keyboard-interactive`) and the limits below. The manifest check reads
  them, so the daemon has no configuration file and erXos adds no
  configuration parser.

The manifest check refuses an SSH domain row that holds any device, any
partition window, any other facet of the system domain, or an
`login` facet the login design's table does not give it, or any files grant but
`ssh_state`'s, so the domain that parses SSH holds only its listener,
its login facet and its host key, through `ssh_state` before the vault
and the vault's facet from stage 4. In a release manifest the check
refuses an SSH domain without the vault's host key facet, and so, before
the vault, any SSH domain at all, and refuses the `record_volume` window
([Root's login keys on the medium](#roots-login-keys-on-the-medium)); `erx_ssh` starts
no daemon under a release's build facts, as `erx_ssh_dev` does at stage
1. So a release build reads no `authorized_keys` and admits no
development key. The system manifest lists the facet in the checked-in
facet table with this section as its justification.

The website offers three images, and each takes the SSH domain on its
own terms; all are development builds:

* **The browser demo** is the site's own boot image, built from the
  website's manifest, which leaves out the domains the board record's
  `site_leaves_out` names (`Platform#site_manifest_source`); `ssh` is one
  of those names, so the demo holds no SSH domain and no `record_volume`
  window. No one can write the medium of an image that runs in a
  browser, so its SSH domain could never be given a key and would only
  take room.
* **The QEMU release medium** is the page's QEMU virt download
  ([site/README.md](../site/README.md)): the medium the release medium's
  writer (`tools/lib/erx/release_medium.rb`) packs from the development
  manifest, with its record partition formatted as the card's, and the
  QEMU command line that boots it. It is not the browser demo's image.
* **The Raspberry Pi's card** is packed from the development manifest
  too.

Both downloadable media are the published media of the development
manifest (`ProductionImage::MediumKind.published`), which carry the
kiosk, so they hold the SSH domain and the `record_volume` window, and their
record volume holds no `authorized_keys` ([Login keys](#login-keys)).
Until whoever writes the medium adds the file, the domain listens and
every key login answers `no_match`; once it is added, the next boot logs
root in with it.

The harness boots of a medium (`MediumBoot`, which the medium suite and
the G5 boot benchmark start from, `tools/lib/erx/medium_boot.rb:499`
and `tools/lib/erx/bench_g5.rb:82`) pack their medium from
`site_manifest_source`, the browser demo's manifest, so they carry no
SSH domain; the QEMU test of a downloadable medium
([Verification](#verification)) needs one packed as the published medium,
an item in `TODO.md`.

`erx_ssh` starts the daemon with `ssh:daemon/3` on a socket listening
through the grant, as `gen_tcp` does in every domain
([design-network-stack.md](design-network-stack.md)), with the options of
[Algorithm policy](#algorithm-policy) and [Limits](#limits-and-who-pays),
`key_cb` set to `erx_ssh_keys`, `ssh_cli` set to `erx_ssh_cli`,
`pwdfun/4` calling the login facet, `parallel_login` true, `subsystems`
`[{"sftp", {erx_ssh_cli, [sftp]}}]` ([SFTP](#sftp)) and
`tcpip_tunnel_in` and `tcpip_tunnel_out` false. With
`parallel_login` true each accepted connection runs its key exchange and
authentication in a process of its own, so a client that stalls before
logging in holds only its own slot and never the acceptor. Each
connection is a process tree of the domain, so a malformed message ends
at most that connection.

### Host keys

The machine has one SSH host key, Ed25519, and offers only it.

* **With the vault** (stage 4), the key is a machine key in the vault's
  machine file, made by the vault at its first request after an
  installation, and the SSH domain holds the `{ssh_host, "ssh"}` key
  facet. `erx_ssh_keys:host_key/2` returns `{ok, {ssh2_pubkey, Blob}}` and
  `sign/3` asks the facet to sign the exchange hash
  ([design-system.md](design-system.md#the-vault)). The key's bytes never
  enter the SSH domain, so a compromise of the domain signs only while it
  lasts and steals nothing that outlives it. The login facet reads the
  key's public blob from the vault when it starts, and compares it with
  each key login's exchange ([Logging in](#logging-in)).
* **Before the vault** (stages 1 to 3, development builds only), the key
  is the file `ssh_host_ed25519_key` in OpenSSH's private key format,
  read and written with OTP's `ssh_file`. At stage 1 it lies in
  `/data/ssh`, written through root's session. From stage 2 the SSH
  domain reaches it through `ssh_state`, a files service of the storage
  domain rooted at the data volume's `ssh/` directory, `/data/ssh` in
  root's namespace, named in `abi/manifest.txt` by `ssh_state_service`
  and granted read-write to the SSH domain alone, which the manifest check
  holds, as the `packages` service is rooted at the volume's `packages/`
  by `packages_service` (`config/manifest/development.txt`), so the domain that
  parses the network reaches that directory and no principal's files. It makes the key when the file is
  missing; a file that does not decode stops the daemon with a log line
  naming the file, and nothing makes a new key in its place, because a
  host key that changes silently teaches users to accept the warning that
  guards against interception. Removing the file is how a developer asks
  for a new key. The release manifest check refuses an SSH domain without
  the host key facet, so this arrangement never reaches a release.

Either way the key persists across reboots and updates and changes only
at a fresh installation (S7). A key made on a boot whose seed is weak,
as a boot's on Fiasco is when its device tree carries no seed, is as
guessable as that seed; the daemon logs `host key made on a weak seed`
once at each start while it uses such a key, a residual recorded in
`TODO.md`.

### Logging in

The daemon offers `publickey` and `keyboard-interactive`, FreeBSD's
default pair, and not `password`. Both reach the same facet.

**The login facet.** The SSH domain logs people in through the system
domain's `login` facet ([design-login.md](design-login.md)), which every
front end holds. Its grant lists four operations: `cookie`, `key_ok`,
`login_key` and `login_passphrase`. The connection's state machine
process, which runs both the exchange and authentication, makes every
call, so the facet keys each outstanding cookie by that process, and the
session a login starts ends when that process ends, which the domain
service watches from the session's start ([A session ends with what it
was started for](design-login.md#a-session-ends-with-what-it-was-started-for)).
The facet tells the SSH domain's processes apart only by the SSH
domain's own word, so keeping each connection's cookie to its own
process is the daemon's bookkeeping; what the facet guarantees is that
no other domain reaches them.
The checks SSH's operations make:

| Operation | Checks |
| --- | --- |
| `cookie()` | 16 bytes from `erx_bytes:entropy/1`, kept as the **outstanding cookie** of the calling connection process for the login grace, 120 s; a new one replaces its last, and it goes when the process ends, when a key login with it succeeds or when the grace ends |
| `key_ok(User, KeyBlob)` | `User` names an enrolled principal whose login keys hold `KeyBlob`; the same `false` for an unknown principal and an unknown key |
| `login_key(User, Exchange, Alg, KeyBlob, Sig, Peer)` | as `key_ok`; `Alg` is `ssh-ed25519`; `Exchange` is the hash input of the connection's first key exchange, at most 64 KiB, which begins with five length-prefixed strings: the client's and the server's version lines, the client's and the server's `SSH_MSG_KEXINIT` payloads, and the host key. The server's payload begins with the byte `SSH_MSG_KEXINIT` and the calling process's outstanding cookie, and the host key is this machine's. The facet takes the SHA-256 of `Exchange` as the session identifier, builds the signed data of RFC 4252 section 7 itself from it, `User`, the service `ssh-connection`, `Alg` and `KeyBlob`, and checks the signature in `Sig`, the 83-byte signature blob of the name `ssh-ed25519` and 64 bytes, over that data with the system domain's Ed25519 verifier. A match retires the cookie |
| `login_passphrase(User, Passphrase, Peer)` | the login design's passphrase check, under the network limits ([design-login.md](design-login.md#the-passphrase-check)) |

Answers are the login design's
([Refusals and error results](design-login.md#refusals-and-error-results)).

**A key login is bound to one fresh exchange with this machine.** The
construction: the facet chooses the cookie of the server's first
`SSH_MSG_KEXINIT` on each connection, and derives the session identifier
itself from that connection's first exchange. A client signs for a
session identifier only after it has checked the host key's signature
over the same hash, under a host key it accepts for the name it dialled
(RFC 4253, section 8). So when the input whose SHA-256 a client's
signature covers holds the facet's own outstanding cookie in the server's
`SSH_MSG_KEXINIT` and this machine's host key, that client completed,
after the facet chose the cookie, an exchange in which it accepted this
machine's host key. Each requirement follows:

* **Freshness.** A cookie the facet did not issue, one past its 120 s, or
  one a login has already used answers `no_match`. So neither a signature
  the principal made at another server nor a login the SSH domain watched
  here earlier, in this boot or a past one, opens a session. Across boots
  the facet's cookies, 128 bits from the kernel's generator, do not repeat
  while that generator is well seeded; on a weak seed, as on a Fiasco
  boot whose device tree carries none, they are as guessable as the seed,
  a residual recorded in `TODO.md`.
* **Binding to this machine.** An exchange whose host key is another
  host's answers `no_match`, so a signature made for any other server,
  whoever chose its cookie, opens nothing here.
* **Nothing remembered.** The facet keeps only outstanding cookies, one
  for each live connection process of the SSH domain, each for at most
  120 s, and drops a connection's cookie when its process exits. A
  connection that closes takes its cookie with it, so no client, however
  many short connections it makes, can push a waiting login's cookie
  out. Losing a cookie fails only the login in progress on its
  connection, so a restart of the facet and the SSH domain's end lose
  nothing a guarantee rests on, and no record of past logins grows with
  them.
* **One reading of the input.** The five strings are length-prefixed, so
  a byte string has one parse, and finding two different inputs with the
  same SHA-256 hash is computationally infeasible: the fields the facet
  checked are the fields the client hashed. The facet hashes the bytes
  it was given, unchanged, never a re-encoding of what it decoded. What
  follows the host key, the exchange values and the shared secret,
  differs between exchange methods and is hashed without being read, so
  the facet names no method.
* **One hash.** Every exchange the daemon offers hashes with SHA-256
  ([Algorithm policy](#algorithm-policy)), which the system domain
  computes with `erx_bytes:sha256/1`, a per-byte primitive of every
  runtime image ([design-runtime.md](design-runtime.md#per-byte-primitives)).

The cost is twofold: the exchange input carries the exchange's shared
secret into the system domain, which hashes it, never logs it and keeps
nothing of it; and the daemon offers neither NIST exchange whose hash is
SHA-384 or SHA-512, so the facet has one hash and no table from exchange
methods to hashes ([Algorithm policy](#algorithm-policy)). The facet's word is no stronger than the host key's:
while a compromised SSH domain runs, it can ask for cookies and have the
vault sign exchange hashes, so it can complete an exchange as this
machine with a client anywhere ([Security](#security)). OpenSSH's
privilege separation leaves its pre-authentication process the choice of
the session identifier, the first hash it asks the monitor to sign
([Context](#context)); this facet leaves the SSH domain no such choice.

Against the requirements:

* **S2.** The SSH domain supplies the parts of the signed data and the
  exchange's input, never the session identifier or the signed bytes, so
  it cannot make the facet check a signature made for another user,
  service, key, server or exchange. Without the principal's private key
  it starts a session only for a principal whose client completes an
  exchange with it, under this machine's host key, while it runs.
* **S3.** From the network, the system domain receives a key blob of 51
  bytes (the string `ssh-ed25519` and a 32-byte key), a signature blob of
  83 bytes (the same name and 64 bytes) and an exchange input of at most
  64 KiB, each decoded by one bounded Erlang decoder of the facet's,
  `erx_ssh_wire`, with a fuzz target. The decoder compares the fixed
  blobs whole against their one layout (the key blob's matcher is
  `erx_boot_keys:key_blob/1`, which every reader of root's login keys
  shares and `erx_ssh_wire:key_blob/1` calls), and for each of the five strings
  checks its length against the bytes that remain before it takes the
  string; beyond its five strings the exchange input is only hashed. The
  decoder reads a key blob's 32 bytes only as bytes; the verifier decodes
  them as a point, under the rules below. Its Ed25519 verifier is the small
  verifier the update service uses ([design.md](design.md#decisions)),
  never OpenSSL. The vault receives from the network a user name, to look
  up that principal's login keys or passphrase slot, and a passphrase, for
  Argon2id, and from the SSH domain, through its host key facet, 32-byte
  exchange hashes to sign; it parses no SSH structure.
* **The method is decided by the facet, not the SSH domain.** OTP's daemon
  still checks the signature itself first; the facet's answer is the one
  that admits the connection.

**The verifier's acceptance rules.** The facet accepts a signature only
under RFC 8032's procedure, as RFC 8709 requires: `S` is below the group
order `L`; `R` and the public key decode as points under section 5.1.3,
with `y` below `p`, a square root that exists, and not `x = 0` with the
sign bit set; and the group equation holds, in either form section 5.1.7
allows. So a signature altered to `S + L`, which the equation alone would
accept, is refused. Those rules accept a public key of small order, a
point `P` for which `[8]P` is the neutral point, and anyone can make a
signature that such a key accepts, so `add_login_key` refuses a key that
does not decode or whose encoding is one of the eight points of small
order. The facet's tests call the verifier directly, not behind OTP's own
check, and Monocypher 4.0.2 is the verifier
([design.md](design.md#dependencies)), checked by those tests
([Verification](#verification)).

**Login keys are Ed25519 only.** The daemon's `public_key` list is
`ssh-ed25519`, which serves both the host key and user authentication,
since OTP checks a user's algorithm against that list. A user with only
an RSA or ECDSA key logs in with the passphrase, or makes an Ed25519 key.

**Principals.** The SSH user name is the principal's name. A principal
that has not enrolled has no login keys and no passphrase slot, so it
gets `no_match`, the answer for a wrong key; app principals, which never
enrol, cannot log in. A session's limits, quotas and grants are its
template's, and a refused session start (the principal's domain quota
spent, its budget refused) answers `unavailable` and is logged with its
reason.

**What a login opens.** A passphrase login opens the principal's master
key in the vault, as at the console. A key login opens nothing. The
vault keeps a principal's keys open while any session of the principal
lives and destroys them when the last one ends
([design-system.md](design-system.md#the-vault)), so the session of a key
login can use the principal's keys exactly while another session of the
principal has them open, and keeps them open while it lives; when none
does, it has no keys, and a user who needs them logs in with the
passphrase. The keys belong to the principal, not to one of its
sessions, whichever way the session began. Keys open only to sessions
that gave the passphrase themselves would need the vault to record each
session's unlock; that record belongs to the login service
([design-login.md](design-login.md#risks-and-open-decisions), 3).

**OTP's hooks.** When the key callback module exports them, the daemon
asks `kex_cookie/1` for the cookie of each connection's first
`SSH_MSG_KEXINIT`, keeps that exchange's hash input until authentication
succeeds, and has `ssh_auth:verify_sig/7` call `verify_user/6` with it
and the 83-byte signature blob after its own checks
([Edits to OTP's ssh](#edits-to-otps-ssh)).
`erx_ssh_keys:kex_cookie/1` calls `cookie`, and a connection whose cookie
the facet refuses closes before its exchange; `verify_user/6` calls
`login_key` and stores `{ok, Line}` in the login table under the
connection's process; `is_auth_key/3` calls `key_ok`; `pwdfun/4` calls
`login_passphrase` and stores the line the same way. A connection whose
table row is missing when a channel asks for its line has not logged in
through the facet and is closed.

### Login keys

Each principal's login keys are a list of Ed25519 public keys kept by the
vault, in the principal's own file, in a section sealed under a key
derived from the machine's master key and the principal's name, so the
vault reads them at any time without the principal's passphrase, nothing
that writes the medium under the `device` or `tpm` backend can add one,
and they go with the file when it is removed
([design-system.md](design-system.md#the-vault)).

* **Adding a key needs the passphrase**, as changing it does: the
  session's `sshkeys add FILE` command reads an OpenSSH public key line
  with OTP's `ssh_file:decode/2` in the session, asks for the passphrase
  at its tty, and sends the key's blob and the passphrase through the
  session's credentials facet of the principal service to the vault,
  which checks the passphrase and publishes the file through its owner.
  The principal service refuses a blob that `erx_ssh_wire` does not
  decode or whose key is of small order
  ([Logging in](#logging-in)). A session left open, or a program in it,
  cannot add a way in on its own.
* **Removing a key** (`sshkeys del FINGERPRINT`) and listing them
  (`sshkeys`, printing each key in `authorized_keys` format with its
  SHA-256 fingerprint) need no passphrase, since they add no authority.
* **The first key** is added from a session of a passphrase login, at the
  console or over SSH, so presence at the machine stays the root of
  trust for enrolment.

Once the vault keeps the login keys there is no `~/.ssh/authorized_keys`:
a file the principals' storage domain serves, which every program of the session can write, would let
anyone who writes the data partition, or anything running in the
session, add a login. `~/.ssh/known_hosts` and `~/.ssh/config` stay
ordinary files of the principal, used by clients as on FreeBSD.

**Before the vault** (stages 1 to 3, development builds only), `root`
is the one principal that logs in, and its login keys are the lines of
root's home copy, `/root/.ssh/authorized_keys`, FreeBSD's place. As on
Raspberry Pi OS, whoever prepares the medium writes `authorized_keys`
into the root directory of the medium's record partition, the FAT
volume that holds the boot-selection record, before the first boot, and
the first boot imports it into the home copy; from then on only the
home copy is read
([Root's login keys on the medium](#roots-login-keys-on-the-medium)).
Root's session can write the home copy, so whatever runs in it can add
a login that lasts: a limitation of the development builds before the
vault, stated with 0.1's known limitations.
The host key is made at the first boot ([Host keys](#host-keys)).

The development login key is the clone's Ed25519 pair that
`tools/erx setup`, or the first image build that needs it, makes with
the host's `ssh-keygen` in `erxos/dev-key` under git's common directory,
so every worktree of a clone shares it and no commit holds it
(`tools/lib/erx/dev_key.rb`). For an image a QEMU harness logs in to,
the image build writes the key's public line, without its comment, as
the record volume's `authorized_keys`, as a user would. Only the
harnesses that log in pass the key to the image build, which a
chokepoint check holds (`Checks::LOGIN_KEY_BUILDERS`), so the media the
website offers for download carry no `authorized_keys`, and whoever
writes one of them to a card or disk adds their own
([The SSH domain](#the-ssh-domain)). The private half stays on the host.
`tools/erx ssh` runs the host's `ssh` with that key, the guest's
forwarded port and no configuration file, and checks the guest's host
key under one alias against a known-hosts file of the boot's own, in
the boot's directory: it starts empty with each boot, as the guest's
`/data` and so its host key do, so `ssh` adds the key on first use and
refuses a changed one for the rest of the boot. `ssh` holds the
operator's terminal, so the session's bytes reach it unchanged, as with
any `ssh` to a UNIX host: a session with a pseudo-terminal is a tty, and a
program's output to a tty is its own. Text attributed to the guest, such
as log records and names, keeps going through each sink's escaping
function, and development builds run trusted code only. The facet
admits root's keys from the medium for `root` alone. It issues
cookies, derives each login's session identifier and checks the
signature with the system domain's Ed25519 verifier as at stage 4, so a
compromised SSH domain starts root's session only while a client holding
one of root's keys connects to it. It compares no host key until the
vault holds it: before then the SSH domain holds the key's file, so the
comparison would add nothing against a compromised SSH domain. That gap
and the host key's file are a development-build residual recorded in
`TODO.md`. `login_passphrase` answers `unavailable`, since no passphrase
exists.

### Root's login keys on the medium

The construction: **the file is read at the edge, only until root's
home copy exists, and the system domain receives only key blobs.** The
storage domain that serves `system` reads `authorized_keys` through a
read-only window on the record partition when the tree's file is first
read, decodes its lines, and serves the keys
they name as a read-only tree of one file holding each key's 51-byte
blob after the other. The login facet reads that file and checks each
blob with `erx_ssh_wire`, the decoder it already has for the blobs a
login carries. So the system domain gains no FAT reader, no base64
decoder and no OpenSSH line parser, and what reaches it from the medium
is what reaches it from the network: fixed-format key blobs (S3).

**The import.** Root's session imports the keys once, in the process
of `erx_ssh_dev:boot/1`, after its daemon listens and the session holds
its `home` facet. Only while `/root/.ssh/authorized_keys` is absent, it
reads `login_keys`' `root`, at most 817 bytes, and when that answers at
least one key it writes each as one canonical `ssh-ed25519` line, keeping
only the keys `erx_boot_keys:decode/1` takes back from those lines, in a
`.ssh` directory of mode 0700, the file 0600, whole and synced under
another name and renamed into place, so the home copy is absent or
whole. The import waits for the session's `home` and `login_keys`
facets with `erx_facets:await/3`
([design-system.md](design-system.md#waiting-for-a-grant)), as the
daemon's start waits for `net` and `data`. Each stage has ten minutes
of its own, one absolute deadline over its waits: the daemon's start
from the boot, the import from the daemon's start, so a daemon that
starts late still leaves the import its whole ten minutes. `eagain`,
which the tree answers while the storage domain's reader runs, and
`eio`, which holds until the storage domain restarts, write nothing and
are tried again every half second within the import's ten minutes,
since an installed facet does not announce that its server has become
able to answer. An answer of no
key, of no whole number of blobs within 16, or of blobs that are no
Ed25519 key writes no file, so no empty home copy shuts the medium's
keys out. A home copy that is there, whatever it holds, is never read
for the import or replaced: editing it adds and removes keys afterwards,
and deleting it imports the medium's keys again at the next boot. A boot
whose session has its home copy never asks the tree, so the storage
domain reads no sector of the record volume. A home copy is looked for
at each attempt, so the import never replaces one present when it
looks; one root's session creates in the moment between that look and
the rename is replaced.

**Where the file lies.** The record partition is the medium's first
entry, a FAT16 volume that a computer the medium is put into mounts
as a disk ([design-storage.md](design-storage.md#data-model)). It
belongs to neither slot: an update writes its two record sectors and
nothing else of it, so a file written there survives every update. A
slot's boot partition would not do: an update replaces the spare's
boot partition whole, the check of a slot hashes its boot partition whole
([design-storage.md](design-storage.md#invariants), U5), and no domain
parses a boot partition's FAT. A computer shows a card's two FAT
volumes, the record partition and the committed slot's boot partition,
and users look for their first-boot files on the one named for the
system, so the record volume is labelled `ERXOS` and the slots' boot
partitions `ERXSLOTA` and `ERXSLOTB`
([design-platforms.md](design-platforms.md#slots-and-the-boot-selection-record)),
and the [install guide](guide/raspberry-pi-4.md#what-is-on-the-card)
names `ERXOS` as the volume that takes the file.
On QEMU the medium's record partition is
the same FAT16 volume as the card's, with the record its
one file; a harness that passes a key adds
`authorized_keys` to its own fresh copy of the medium, never to the
medium as written, so the file lies at the same place on both, and the
harness, which reads only the record's sector, finds the record where
it was. A user adds the file to a QEMU
medium as to a card, by attaching the image on the host and copying the
file onto its first FAT volume.

**No domain writes it.** The record partition has three windows: the
slot writer's two, on the record's sector (`boot_selection`) and on the
reset count's (`reset_count`), one sector each, and the storage
domain's `record_volume` window on the whole partition, which
`abi/manifest.txt` does not mark writable, so its driver refuses every
write to it. No window grants a write to any other sector of the
partition, and the reader refuses a volume whose FATs or root directory
cover either sector
([design-storage.md](design-storage.md#removable-media-fat)), so the FAT,
the root directory and the file are written by no domain, whatever the
domains do; the one code that could, the block
driver, alone calls the device ([design-storage.md](design-storage.md#invariants),
PW1). Physical write access to the medium is root's login, a known
limitation of every build before the vault, stated in the user
documentation.

**The accepted format** is a subset of sshd(8)'s AUTHORIZED_KEYS FILE
FORMAT ([Sources](#sources)), read as bytes:

* a line ends at a line feed, and a carriage return just before it is
  dropped, so a file saved on Windows reads the same; a last line
  without its line feed counts;
* leading spaces and tabs are skipped; a line that is then empty, or
  starts with `#`, is ignored, as sshd ignores it;
* any other line is fields separated by runs of spaces and tabs: the
  first is exactly `ssh-ed25519`; the second is the key, exactly 68
  characters of RFC 4648's base64 alphabet, which decode to 51 bytes
  with no padding and no spare bits, so each blob has one spelling, and
  which must be the blob of the name `ssh-ed25519` and 32 bytes; anything after the key is
  the comment, which is never read or shown.

**Options are refused, not ignored.** sshd's options field comes before
the key type, and each option limits or widens what a login with the key
may do (`restrict`, `command=`, `from=`, `no-pty`, `permitopen=`). The
daemon has none of those controls, and ignoring an option would give the
key more than its line grants. So a line whose first field is not
`ssh-ed25519`, whether it carries options, another key type or
`cert-authority`, is not a key. sshd skips a line it cannot use and reads
on (`auth2-pubkeyfile.c:436-440`, `:286-301`); so does the reader, since
a skipped line adds no authority and the other lines stay usable.

**Bounds.** Each bound is a plain number the reader checks before it
uses what the bound covers:

| Bound | Value | Past it |
| --- | --- | --- |
| the file | 16 KiB | the whole file is refused |
| a line, its line feed included | 1024 bytes | the line is skipped |
| keys | 16 | the whole file is refused |

An `ssh-ed25519` line is 80 bytes and its comment; sshd's 8 KiB lines
are for RSA keys, which the file does not take. A bound on the whole
file refuses it whole, since keeping a prefix would drop keys silently;
a fault of one line skips that line.

**Diagnostics.** Each finding is one log record of the storage domain,
which reaches the console, naming the file, the line number and one
reason of a closed set: `not a plain ssh-ed25519 key`, `key does not
decode` and `line longer than 1024 bytes` for a skipped line, and for
the file `no authorized_keys`, `longer than 16 KiB`, `more than 16
keys`, `the record partition is not its FAT volume`
([design-storage.md](design-storage.md#removable-media-fat)) and `does
not read`, each a refusal the pure functions below decide, and
`read failed`, when a sector read through the window fails or the reader
ends without a result.
No byte of the file is shown, so nothing a user wrote reaches a sink.
When it first reads a result the facet logs `root: N SSH login keys from
the medium`, or `root has no SSH login key` when there are none. A
missing, empty or wholly refused file is a boot with no SSH login, since
no passphrase exists before the vault; the console login is unaffected.

**Who publishes it.** The tree is `login_keys`, of one file, `root`, a
files service named in `abi/manifest.txt` by `login_keys_service`, as
`packages` is by `packages_service`. The manifest check makes its
publisher the reader by the rule it already applies to `system`: a manifest with a `record_volume`
window holds exactly one service of that name, of the files interface,
whose server is the window's holder, and a manifest without the window
holds none; every grant of the service is read-only and the system
domain's or the system principal's session template's (`@session.system` in
the development manifest), whose import of [stage 1](#stages) reads
root's keys; a manifest holds at most one `record_volume` window; and that
window lies only on the domain that holds the `system` window. So the domain that serves root's keys is the
one whose read-only window covers the record partition, and no manifest
can name another, the SSH domain among them, as their source.

The holder learns that it holds the window from the manifest alone. On
erXos's kernel the device service names the window for the holder its
manifest row names ([design-storage.md](design-storage.md#invariants),
PW1). On Fiasco, whose block service reads no manifest, the
domain library marks it in the one record it already writes for that
holder alone: `-erx_record system_image` gains a sixth word,
`record_volume`, exactly when the manifest holds the window
([design-fiasco.md](design-fiasco.md#the-booted-slot)). From that word
the block table starts the read-only `record_volume` window, whatever
slot the boot names, and the storage domain starts the tree's mint on
it; a domain whose record lacks the word, or
has no record, starts neither, so no other domain serves `login_keys`
or reads the record partition. The word grants nothing by itself: the
window is a range of the block device, which only that holder holds.

**How the facet reads it.** The facet reads `root` from its start until
it holds 817 bytes, one past 16 keys' 816, or meets its end, each read
asking for no more than what is left of the 817, on a file opened
without read-ahead, so no request asks for more than the read does. It
never asks the file's size, so a server that overstates it, or a file
that never ends, costs at most 817 bytes. An answer longer than its
request is refused by the files client, `erx_file_remote`, with `eio`,
which the facet treats as any failed read below. The bytes then go to one pure function,
`erx_login:medium_keys/1`, which refuses the whole file, with a log record, when its length is not a multiple of
51 or is past 16 keys', or when a blob does not decode under
`erx_ssh_wire`'s key layout or is one of the eight points of small order
that `add_login_key` refuses ([Logging in](#logging-in)): the blobs are
the reader's output, so a fault in them is the reader's and not a line
to skip.

**When it is there.** The reader takes as long as the medium does, and
the tree's lifecycle keeps that wait from reaching anything but key
logins:

* **One holder owns the result.** The `login_keys` mint runs in the
  storage domain beside `system`'s when the domain's block service
  serves the `record_volume` window, which it does exactly when the
  manifest gives the domain that window ([Who publishes it](#roots-login-keys-on-the-medium)),
  and like every mint it names itself the service's provider before the
  domain's ready report. Its mount only starts the holder, a process
  linked to the mint, and answers its pid as the tree's arguments; the
  mount waits for no read. The holder reads nothing until `root` is first asked for, so a
  boot whose session has its home copy reads no sector of the volume;
  then it spawns the reader with a monitor, answering `eagain` until the
  reader is done, and is the one owner of the published result: the reader's result message is tagged with
  that monitor's reference, so no other message in the storage domain
  can be taken for it; the first of that message and the `'DOWN'` with
  the same reference decides the result, and every later message is
  ignored. The
  holder runs no decoder and reads no sector, so it ends only with the
  mint, and the mint's end, as for every tree, ends its grants. The
  `erx_fs` grants' callbacks ask the holder for `root` and serve its
  answer. So the mint answers the domain service's mint requests at once
  and the system domain's grant is installed inside its 10-second
  deadline (`erx_domain_mints`), however long the reader takes. A mount
  that waited would leave the grant failed at the deadline, and a failed
  grant is tried again only when an incarnation changes, so SSH would
  stay closed for the boot after the reader had finished.
* **What `root` answers.** While the reader runs, a read of `root`
  answers `eagain`, an error and not an empty file, so no client
  mistakes the wait for a result. A result the pure functions decide is
  the file: the blobs, or none when they refuse it, with its finding. A
  sector read that fails, a reader that raises and a reader that ends
  without a result answer `eio`, with the finding `read failed`: the
  medium was not read, so the holder publishes no empty file in its
  place. Once decided, the answer holds for the storage domain's
  incarnation and never changes. So a crafted volume costs SSH logins
  and nothing else, and the domain serves `system` and its other trees
  without waiting for the reader.
* **The facet's copy is keyed to the grant.** The grant is the pid
  `erx:cap(login_keys)` answers, the facet the domain service installed
  in the system domain's table of facets, which a later install of the
  same name replaces. A new storage incarnation is
  a new domain whose mint gives a new facet, so its pid differs from
  every earlier one. At a key login the facet takes that pid, reads
  `root` through it, and keeps the file it read, keys or none, together
  with the pid it took before the read. At the next key login it takes
  the pid again and uses the copy only when the two are equal; a
  different pid, or none, drops the copy and reads again. So each storage
  incarnation is read once, and a copy read through a grant that a
  restart has since replaced is never used, even when the read was still
  in flight at the restart. A read that fails, `eagain`, `eio` or a grant
  that is gone or not yet installed, answers that login `unavailable`
  and keeps nothing, so the next login reads again.
* **A restart reads again.** A restart of the storage domain is a new
  incarnation: it reads the medium again and decides again, and the
  domain service mints the system domain's grant for it afresh, which
  drops the facet's copy. No domain writes the partition, so a medium
  that read before gives the same blobs, and a reader that failed in the
  last incarnation is tried anew; a restart of the facet reads again
  too.

Nothing is written, so a power cut loses nothing. A key added to the
medium takes effect at the next boot that finds no home copy
([The import](#roots-login-keys-on-the-medium)); once root has one, keys
are added to the home copy.

**The code.** The reader is two pure functions run in the storage
domain: `erx_fat_read:root_file/3`, which finds one file of a FAT
volume's root directory by its long name and answers exactly the bytes
its entry's size gives, never its last cluster's slack
([design-storage.md](design-storage.md#removable-media-fat)), and
`erx_boot_keys:decode/1`, which returns the blobs and the findings, or
the file's refusal. The system domain's is `erx_login:medium_keys/1`.
Each reads through a cursor and has a fuzz target
([Verification](#verification)).

### Root's passphrase on the medium

Before the vault, a development build checks root's passphrase against a
salted hash beside the keys
([design-login.md](design-login.md#the-passphrase-check), decision 1).
The construction is the keys': **the line is read at the edge, and the
system domain receives only a fixed record.**

* **The file** is `passphrase_hash` on the record volume, `ERXOS`,
  which a user writes on the host with `tools/erx passphrase-hash`, which
  asks for the passphrase twice without echoing it and prints the line,
  and copies onto the volume as `authorized_keys` is. No domain writes it
  ([No domain writes it](#roots-login-keys-on-the-medium)).
* **The accepted form** is one crypt(3) SHA-256 string, as FreeBSD's
  `crypt-sha256.c` writes it, read as bytes: `$5$`; optionally
  `rounds=N$`, with N from 1000 to 100000 in decimal and no leading
  zero; a salt of 1 to 16 characters of crypt's alphabet
  (`./0-9A-Za-z`); `$`; and 43 characters of that alphabet, which decode,
  in `crypt-sha256.c`'s byte order, to the 32-byte hash, with the last
  character's two spare bits zero, so each hash has one spelling. The
  line may end in a line feed, with a carriage return before it, and
  nothing follows. The file is at most 128 bytes. FreeBSD clamps rounds
  out of range; the reader refuses them, so the cost of a derivation
  stays within what one check in the system domain may take.
* **Who reads it.** The `login_keys` reader reads both files, in the
  same storage domain, through the same window and on the same
  lifecycle ([When it is there](#roots-login-keys-on-the-medium)), when
  either file of the tree is first read, and `erx_boot_passphrase:decode/1`
  reads the line through a cursor and answers the record
  `erx_passphrase_hash` lays out, `<<Rounds:32, Hash:32/binary,
  Salt/binary>>`, 37 to 52 bytes. The tree serves it as a second file,
  `root_passphrase`, of mode 0400. A file that is absent or refused is
  served empty, with one log record of the storage domain naming the
  file and one reason: `no passphrase_hash`, `longer than 128 bytes`,
  `not a $5$ SHA-256 crypt string`, the volume's refusals above, or
  `read failed`, which, as for the keys, answers `eio` and not an empty
  file. No byte of the file is logged.
* **What it costs.** Anyone holding the medium can try the hash
  offline, as anyone holding it can read or replace it; physical access
  to the medium is root's login before the vault, as for the keys, and
  the user documentation says so.

### Sessions, ttys and shells

`erx_tty_line` is the session's process behind its line to the SSH
domain, the `tty_line` facet that the session mints for the SSH domain
when a login through the facet names it, as `erx_web_line` is behind the
web domain's ([design-system.md](design-system.md#a-sessions-lines)).
The facet admits the SSH domain's calls, within its `max_request` and
`in_flight`, each from a caller and alias of that domain's, and forwards
each with the channel's domain to `erx_tty_line`; nothing else from
another domain reaches the line process. The interface `tty_line` in
`abi/services/tty_line.txt` lists the operations the line serves, an
operation entering it with the code that serves it, and the messages
the session sends a channel, from a tty or a job's relay, are no operations of it. `erx_tty_line` takes two
requests, each from a channel process of the SSH
domain, and answers each `ok` or
`{error, limited | badarg}`:

* **`{open_tty, Channel, Run, Term, Rows, Columns}`** for a channel that
  asked for a pseudo-terminal and then a shell or a command. The relay
  makes a tty whose master is `Channel` and starts the principal's shell
  on it. From then on the tty and the channel exchange the seven console
  messages, with `window-change` sent as `tty_size` and the channel's end
  or the connection's as `tty_hangup`. The shell's `TERM` is `Term` when
  `abi/terminal.txt` names it and `vt100` otherwise; a size of zero, which
  `pty-req` allows, is taken as 24 rows or 80 columns.
* **`{open_job, Channel, Run}`** for a channel with no pseudo-terminal.
  The session starts the shell with standard input, output and error on
  three of the command shell's message pipes
  ([design-shell.md](design-shell.md#pipelines)), whose other ends the
  job's relay holds, a process of the line, and the relay carries them
  to the channel with the job messages below, so a program's error
  output stays apart from its output, as `git` and `rsync` over SSH
  need.

`Run` says what runs: `shell` runs `rc`, interactive on a tty and reading
commands from standard input in a job, as OpenSSH runs the user's shell
without a tty; `{exec, Command}` runs `rc -c Command`, for an `exec`
request, with `Command` a binary of 1 to 32 KiB holding no NUL byte; and
`sftp`, in `open_job` alone, runs the session's SFTP server for the
`sftp` subsystem ([SFTP](#sftp)). A line answers `limited` past ten open
channels, `max_channels`, and `badarg` to any other shape. The host
tool's SSH route is such a job, an `exec` of the session command `load`
whose standard input carries the modules and whose facets are the
session's ([design-live.md](design-live.md#one-load-three-routes)).

A job's streams are message pipes, not pipes of the pipe server: the
relay and `rc` are both processes of the session, and the session joins
its own processes with message pipes, keeping its pipe server's pipes
for where a program takes part
([design-shell.md](design-shell.md#pipelines)). A program the job
starts gets pipe ends of the pipe server from its starter, whose pumps
join them to the job's streams, so it reads end of file and writes into
`EPIPE` as on any pipe
([design-shell.md](design-shell.md#starting-programs)). The relay never
waits on a pipe: it asks for each write and each read without blocking
and takes the answer as a message, and at `job_eof` it closes standard
input's writing end while it goes on running, so `rc` reads end of file
while the job's output still flows.

The job's group leader is the relay's group, a process the relay starts
linked to it. What the job's processes print through `io` the group
writes to the job's standard error, whatever a command's own
redirection, and never to standard output, which stays byte-clean;
every other request it answers `{error, enotsup}`, and a `requests`
list holding one `{error, request}`, as every group does. Input is
refused as the command shell's group refuses it to every process but
its shell
([design-shell.md](design-shell.md#the-terminal-relays-protocol)), and
`setopts`, `getopts` and `get_geometry` because a job has no terminal,
as `io:columns/0` reports for any device that is not one. The group
makes each request's bytes, running the function a `put_chars` names
as stock OTP's group runs it, and, unlike that group, which hands each
request to its driver and goes on, serves one request at a time: it
writes the bytes to standard error, waiting for room, and answers once
they have entered. So a channel that takes no output stops the job's
printers in their own requests, each printing process with at most one
waiting, and the relay holds none of the job's output and runs none of
its code: it always hears its channel, and its end kills the group. The group writes to standard error without holding it,
so the stream still ends when `rc` does. On a tty, the command shell's
group writes `io` output to the terminal, which is standard error
there, so output follows one rule in both.

A job's channel and its relay exchange seven closed messages, each
checked by its receiver. The relay's reach the channel in the session's
envelope, from a name `open_job`'s answer hands the channel, so the line
process itself sends a front end nothing
([design-system.md](design-system.md#a-sessions-lines)); how the
channel's reach their job, named and delivered without loss, is the
open question "How a job's messages reach their job"
([Risks and open questions](#risks-and-open-questions)):

| Message | Direction | The receiver's check | If it fails |
| --- | --- | --- | --- |
| `{job_input, Bytes}` | channel to relay | a binary of at most 32 KiB, the channel's packet size, with no other `job_input` unanswered and no `job_eof` before it; the relay writes it to standard input's pipe, waiting for room | the relay ends the job, as at `job_hangup` |
| `job_written` | relay to channel | a `job_input` is unanswered; the channel then opens the client's window by its size | the channel closes |
| `job_eof` | channel to relay | none; the relay closes standard input's writing end once what came before it is written, and the job's output and status still flow | not applicable |
| `{job_output, Stream, Bytes}` | relay to channel | `Stream` is `stdout` or `stderr`, `Bytes` a binary of at most 32 KiB, with no other `job_output` unanswered; the channel sends it as channel data or extended data within the client's window | the channel closes |
| `job_sent` | channel to relay | a `job_output` is unanswered; the relay then reads the pipes again | ignored, as a late repeat |
| `job_hangup` | channel to relay | that atom; it holds from then on | not applicable; the relay closes every end and ends the job's programs, as the relay ends a tty's shells at `tty_hangup` |
| `{exited, Status}` | relay or tty to channel | `Status` is an integer from 0 to 255 | the channel closes |
| `{signaled, Signal}` | tty to channel | `Signal` is a member of the signal set `tty_master` in `abi/signals.txt`, `sigint` alone | the channel closes |

`{exited, Status}` serves ttys too, and a tty has a second ending,
`{signaled, Signal}`, for an exec that the tty's `Ctrl-C` ended, with
`Signal` a name of the signal set `tty_master` in
`abi/signals.txt`, `sigint` alone, since `Ctrl-C` is the only
signal that ends an exec on a tty. A tty's ending has only these two
shapes, with `Status` from 0 to 255 and `Signal` in that set, because
the console that makes it maps any other end to status 1
(`erx_console:shell_ending/1`) and hands it to the tty's relay, the
process the channel holds as the tty, which sends it as its last message;
the channel checks it against that set and closes on any other. FreeBSD's `sh -c` dies of the SIGINT
that ends its command (`onint` in `bin/sh/error.c` of FreeBSD 14.2,
lines 117-123), rather than exiting 130, the `$?` a parent shell gives
a command SIGINT ended (`waitforjob` in `bin/sh/jobs.c`, line 1114),
and OpenSSH's `sshd` sends `exit-signal` for a command a signal ended
(`session_exit_message` in `session.c`), so the client sees a signal,
not an exit, on both systems. A hangup needs no ending, since the
channel is gone by then.

The tty's relay, or the job's relay, sends its channel one ending, as
its last message, once what it started on the channel, the
shell on the tty or the job, has ended, every process it started has
ended with it, and its last output has been taken, by `tty_taken` or
`job_sent`, so the ending arrives after every byte of output. The
channel then sends SSH's `exit-status` for `{exited, Status}`, or
`exit-signal` for `{signaled, Signal}`, with the signal's name without
`sig` in capitals (`INT`), no core dump, and an empty message and
language tag; then its end of file and its close, and `tty_hangup` to a
tty. One unanswered message each way bounds what either side holds for
a channel to 32 KiB of input and 32 KiB of output beyond the client's own
window, and a pipe's writer that waits for room carries back-pressure to
the client's window.

Input flows into a tty as `tty_input` messages of at most 4 KiB; the tty
bounds what waits unread, and the channel adjusts the SSH window only as
it sends, so a client that types faster than the program reads loses the
excess as on a line's overrun ([design-live.md](design-live.md#paths)).

At the end of the connection every channel's tty gets `tty_hangup` and
every job's relay `job_hangup`; the connection's process ends, and with
it the login it holds, so the session ends as a console session ends at
log-out. If the SSH domain ends first, the facet ends with it and every session its logins
started ends, as the web's do.

### SFTP

**The `sftp` subsystem is a job.** FreeBSD's `sshd_config` runs
`/usr/libexec/sftp-server` for the `sftp` subsystem ([Context](#context)),
a program run as the user on the channel's standard input and output.
erXos does the same with the job of
[Sessions, ttys and shells](#sessions-ttys-and-shells): the daemon's
`subsystems` option names one subsystem, `sftp`, whose channel module is
`erx_ssh_cli`, started with the argument `sftp`, which OTP's connection
starts on a `subsystem` request as it starts a channel for a shell
(`start_subsystem/4` in `lib/ssh/src/ssh_connection.erl`); at its
`ssh_channel_up` the channel asks its line for `{open_job, Channel,
sftp}`, and from then on the channel and the line exchange the job
messages unchanged. The SSH domain therefore parses no SFTP and holds no
file of the principal's; SFTP reaches only what the session reaches
(S1). A second subsystem on a channel that already runs one, or a shell
or exec, is refused by OTP's connection (RFC 4254, section 6.5).

**The server.** In the session, `Run = sftp` starts `erx_sftp_server`
on the job's three streams instead of `rc`, as OpenSSH's `internal-sftp`
serves SFTP in the session's own process rather than through the user's
shell (`do_child` in `session.c`). `erx_sftp_server` reads standard
input and hands each piece to OTP's `ssh_sftpd`, whose request decoding,
handle table and replies it uses unchanged, with each reply written to
standard output ([Edits to OTP's ssh](#edits-to-otps-ssh)). Its options:

* no `root`, since the session's namespace is already the principal's
  whole reach, and `cwd` the principal's home, so `scp x DEST:` writes
  `x` there;
* `file_handler` OTP's `ssh_sftpd_file`, whose calls are `file`'s, so
  every path resolves through the session's namespace with the session's
  grants, as for any Erlang code of the session;
* `max_handles` 64, and `max_files` 100, so a `READDIR` answers at most
  100 names, as OpenSSH's `sftp-server` sends at most 100 a message
  (`process_readdir` in `sftp-server.c`), where OTP's default, no limit,
  would answer a whole directory at once;
* the version OTP's server offers, which it lowers to the client's at
  `SSH_FXP_INIT`: 3 for OpenSSH's clients.

A request longer than 256 KiB, OTP's `SSH_MAX_PACKET_SIZE`, ends the
server, as a request it cannot decode does, and either ends the job with
status 1 and nothing else; the server writes nothing to its error
output. At the end of its input the server closes every handle and the
job exits 0.

**What `scp` needs.** OpenSSH's `scp` has used SFTP by default since
OpenSSH 9.0 (scp(1)), and asks for the `sftp` subsystem with `ssh -s`
(`do_sftp_connect` in `scp.c`). An upload sends `SSH_FXP_INIT`, a `STAT`
of the target to learn whether it is a directory, `OPEN` for writing,
the `WRITE`s and `CLOSE`, with `FSETSTAT` under `-p` and `MKDIR` under
`-r` (`source_sftp` in `scp.c`, `sftp_upload` in `sftp-client.c`); a
download sends `STAT`, `OPEN`, the `READ`s and `CLOSE`, and `-r` adds
`OPENDIR` and `READDIR`. Each is a request of SFTP version 3 that
`ssh_sftpd` serves. A target of `~user/...` needs the
`expand-path@openssh.com` extension, which `ssh_sftpd` does not offer, so
`scp` refuses it with its own message; `~/x` and `x` it sends relative
to the home (`prepare_remote_path` in `scp.c`). `scp -O`, the legacy
protocol, runs `scp -t` through `exec`, which names no command of
erXos, so it fails with `rc`'s `not found`. `sftp` and `sshfs` speak the
same protocol and work within the same requests.

### Algorithm policy

The daemon's `preferred_algorithms` follow FreeBSD's server lists, in
FreeBSD's order, less what OTP does not implement and the exchanges whose
hash is not SHA-256:

| Class | Offered |
| --- | --- |
| key exchange | `mlkem768x25519-sha256`, `curve25519-sha256`, `curve25519-sha256@libssh.org`, `ecdh-sha2-nistp256` |
| host key and user key | `ssh-ed25519` |
| cipher | `chacha20-poly1305@openssh.com`, `aes128-gcm@openssh.com`, `aes256-gcm@openssh.com`, `aes128-ctr`, `aes192-ctr`, `aes256-ctr` |
| MAC | `hmac-sha2-256-etm@openssh.com`, `hmac-sha2-512-etm@openssh.com`, `hmac-sha1-etm@openssh.com`, `hmac-sha2-256`, `hmac-sha2-512`, `hmac-sha1` |
| compression | `none` |

OTP has neither `sntrup761x25519-sha512` nor the UMAC family. Every
exchange offered hashes with SHA-256 in OTP (`sha/1`,
`ssh_transport.erl:2395-2416`), so the login facet has one hash
([Logging in](#logging-in)). The server offers neither
`ecdh-sha2-nistp384` nor `ecdh-sha2-nistp521`, which hash with SHA-384
and SHA-512: the facet would then need SHA-384 and SHA-512 exposed to
it, a choice of hash by exchange method, and tests of each. Neither
hash is a new implementation in the system domain, since the Ed25519
verifier computes SHA-512 (RFC 8032, section 5.1.7) and SHA-384 is
SHA-512's processing with other initial values and a shorter output
(RFC 6234, section 6.4); what the narrower list saves is that method
table and its tests. A client with FreeBSD's default list offers the
two only after `mlkem768x25519-sha256`, the Curve25519 exchanges and
`ecdh-sha2-nistp256` (`KEX_CLIENT_KEX`, `myproposal.h:37-41`), so it
never needs them here. The host key list is narrower
than FreeBSD's because the machine has one Ed25519 key. Compression is
off, so no compressed length reveals anything of the plaintext. The lists
are fixed by the release, so no client can negotiate below them (S6).
The strict key exchange is offered and used with every client that
offers it too; a client that does not offer it connects without it, and
its connection is open to the prefix truncation that strict exchange
closes, which the log record of each connection shows.

### Limits and who pays

| Limit | Value | Bounds | Paid by |
| --- | --- | --- | --- |
| connections at once (`max_sessions`) | 64 | the SSH domain's memory and sockets | the SSH domain's budget and grant |
| logins in progress (`parallel_login`) | true: one process per connection | a stalled connection holds its own slot, never the acceptor | the SSH domain |
| login grace (`negotiation_timeout`) | 120 s, FreeBSD's `LoginGraceTime` | how long an unauthenticated connection holds a slot | the SSH domain |
| version line (`hello_timeout`) | 30 s | idle connections before the version line | the SSH domain |
| authentication attempts per connection (`max_auth_tries`) | 6, FreeBSD's `MaxAuthTries`, counted as FreeBSD counts them ([Context](#context)) but for two cases recorded in `TODO.md`: an unoffered method as the first request goes free, and a change of user name between requests is not refused | guesses per connection | the SSH domain |
| outstanding cookies and logins | one row per live connection process, its cookie for at most 120 s, dropped when its process exits; past the grant's `logins`, 128, `cookie` answers `unavailable` | the login facet's memory | the system domain, bounded by the grant |
| failed logins per name | the vault's 5 in 60 s from network connections | guessing across connections | the vault, on its own grant |
| channels per connection (`max_channels`) | 10, FreeBSD's `MaxSessions` | ttys and jobs per connection | the session, for each tty or job |
| a channel's receive window and packet | 64 KiB and 32 KiB | what the SSH domain holds for one channel | the SSH domain |
| a job's messages in flight | one each way, 32 KiB each | what the line and the channel hold beyond the window | the session and the SSH domain |
| an SFTP job | 64 handles, requests of at most 256 KiB, 100 names a `READDIR` | the server's handle table and its buffer | the session |
| sessions per principal | the principal's domain quota | session domains | the principal's budget |

The SSH domain's worst case is 64 connections of 10 channels each
holding a full window, 40 MiB, within its own budget, so no client makes
it take memory from anyone else. The SSH domain's runtime, with
`crypto` and `ssh` loaded, is about 30 MiB, an estimate its first
measurement replaces, and each login starts a session domain of the
session template's 36 MiB, so the QEMU manifests' memory figures, and
the guest's RAM where they need it, grow by the SSH domain and one
session per login the harnesses hold at once. FreeBSD's random early drop of
unauthenticated connections (`MaxStartups`) has no OTP counterpart: a
flood of unauthenticated connections fills the 64 slots until their
grace ends, refusing others; it fails safe and is recorded as a
residual in `TODO.md`. A flood of short connections takes no waiting
login's cookie, since each cookie ends with its connection.

### Logging

Every connection, authentication result and session start or end is a
structured log record of the SSH domain: the peer's address and port,
the client's version string, the user name, the method, the key's
SHA-256 fingerprint, whether the strict key exchange was negotiated and
the outcome. The version string and the user name are the network's
text, so they are record fields that only the log sink's escaper
renders, with tab and newline escaped, as for any text attributed to a
source (S4). OTP's own `ssh` log lines go through the same handler,
`erx_log_h`, with `max_log_item_len` bounding what they quote. The
principal service logs each session the facet starts, under the system
domain's name, which is the record of who logged in, with the SSH
domain's claimed peer marked as its claim, and each login key added or
removed, with its fingerprint and the line of the session that asked.
No record carries a passphrase, an exchange input or a session
identifier.

## Invariants

| Invariant | Holds because |
| --- | --- |
| **H1.** A session started over SSH holds its template's facets and nothing else | the domain service makes it from the template; the facet chooses only the start map |
| **H2.** No session starts without a check outside the SSH domain | the `login` facet is the SSH domain's only way to a session, and it decides from the vault or the verifier |
| **H3.** The SSH domain holds no authority over principals | the manifest check limits its row to its grant, the login facet and the host key facet |
| **H4.** A connection's end ends what it started | `tty_hangup` and `job_hangup` end its shells and jobs; the connection process's end ends its login and its session; the facet's end ends all of them |
| **H5.** The system domain runs no OpenSSL; neither it nor the vault parses an SSH packet, and the vault decodes no SSH structure | the facet's decoder compares two fixed-format blobs against their one layout and takes five length-prefixed strings, each checked against the bytes that remain, in Erlang; the facet hashes the input as given with `erx_bytes:sha256/1` and checks Ed25519 with the update verifier, which alone decodes a key's bytes as a point; the vault sees lookups, passphrases, 32-byte exchange hashes and key blobs the principal service has already decoded |
| **H6.** The host key never changes silently | it is made only when absent, and a corrupt one stops the daemon |
| **H7.** A key login names one exchange that began after the facet chose its cookie and that carried this machine's host key | the facet derives the session identifier from the exchange input itself, finds its own outstanding cookie and the host key in that input, and retires the cookie at the login |
| **H8.** Before the vault, root's login keys are the lines of root's home copy, `/root/.ssh/authorized_keys`, and nothing else; the home copy is written from the medium's `authorized_keys` only while it is absent and only with at least one key, and is absent or whole; no domain can write the medium's file; and the only grants of `login_keys` are read-only, the system domain's and, for stage 1's import, the system principal's session template's, and serve only key blobs. Root's session can write the home copy, a development-build limitation | the slot writer's record windows are one sector each, the reader refuses a volume whose FATs or root directory cover either sector, and the reader's `record_volume` window is not writable; the manifest check makes `login_keys`' server the holder of that window and its grants read-only and the system domain's or root's session template's; the storage domain decodes the lines and serves 51-byte blobs; the import looks for the home copy before it reads the tree, writes only lines of blobs `erx_boot_keys` takes back, and writes under another name and renames; the daemon reads at most 16 KiB and one byte of each keys file and decodes it with `erx_boot_keys`, and the facet reads at most 817 bytes of blobs and checks each with `erx_ssh_wire` |

## Failure handling

| Failure | Seen as | Result |
| --- | --- | --- |
| a connection's process crashes on a malformed message | its exit | that connection closes; its ttys hang up, its jobs end and its session ends |
| the SSH domain crashes | its exit record | every connection closes and every session its logins started ends; the facet and its cookies end with it; the domain service restarts it under its restart intensity and it listens again |
| the facet's `cookie` answers `unavailable` (the kernel's generator fails) | `kex_cookie/1` raises | that connection closes before its key exchange, with one log line; others go on |
| a cookie past its grace | `login_key` finds it not outstanding | that key login answers `no_match`; the client may try its passphrase or connect again |
| 128 cookies outstanding | `cookie` answers `unavailable` | that connection closes before its key exchange, as when the generator fails; others go on |
| the host key file is missing (before the vault) | `ssh_file` finds none | a new key is made and logged with its fingerprint |
| the host key file does not decode (before the vault) | `ssh_file`'s error | the daemon does not listen; one log line names the file; the domain stays up |
| the vault answers `unavailable` (its partition or backend down) | the host key facet's or login's answer | the daemon waits, retrying every 10 s with one log line, and does not listen until the host key answers; logins answer `unavailable` |
| the login service crashes | the login facet ends, with an atom | the SSH domain takes the facet's end as its own and ends: every connection closes and every session its logins started has already stopped with the facet; the domain service restarts it under its restart intensity, with a new login facet, and it listens again |
| the network domain restarts | the grant's sockets close | the listener and every connection end; `erx_ssh` listens again when the grant answers |
| a session cannot start (quota, budget) | the domain service's refusal | the login answers `unavailable`, logged with the reason; the client sees authentication fail |
| entropy unavailable in the SSH domain | `crypto` raises in the key exchange | that connection closes ([design-crypto.md](design-crypto.md#seeding)) |
| `authorized_keys` missing, empty or refused whole (before the vault) | the reader's finding, and the facet's `root has no SSH login key` | every key login answers `no_match`; the console login is unaffected |
| a line of `authorized_keys` that is not a plain `ssh-ed25519` key, does not decode or is too long | the reader's finding, with the line's number | that line is skipped; the other lines' keys log in |
| the `login_keys` tree still loading, its grant not yet installed, or the storage domain restarting when a key login arrives | the facet's read answers `eagain` or fails | that login answers `unavailable` and nothing is kept; the next one reads again |
| a sector read through the window fails, the reader raises, or its process ends without a result | the holder's monitor, which takes the first of the result and the `'DOWN'` | `root` answers `eio` for the incarnation, logged `read failed`; every key login answers `unavailable`; `system` and the other trees are served throughout; the storage domain's next incarnation reads again and the facet, its copy keyed to the old grant, reads the new one |

## Refusals and error results

The client sees SSH's own results: a refused method or a `no_match` is
`SSH_MSG_USERAUTH_FAILURE`; `limited` and `unavailable` are failures too,
logged with their reason, so a client learns nothing more than a wrong
key; the failure that reaches `max_auth_tries` is answered with a
disconnect; a refused
channel request, a line's `limited` or `badarg` included, is
`SSH_MSG_CHANNEL_FAILURE`, and a refused channel type
`SSH_MSG_CHANNEL_OPEN_FAILURE` with `SSH_OPEN_ADMINISTRATIVELY_PROHIBITED`;
an algorithm mismatch ends the key exchange. The facet's answers are the
closed sets of its table, and `erx_ssh_wire` refuses a blob of any other
length or name, and an exchange input over 64 KiB, short of its five
strings or with a string longer than what remains, with `badarg`, which
the facet answers `no_match`. Within an SFTP job a refused request is
SFTP's own `SSH_FXP_STATUS`, with the code `ssh_sftpd` maps the file
error to, such as `SSH_FX_PERMISSION_DENIED` for a path no grant of the
session writes, and a subsystem other than `sftp` is
`SSH_MSG_CHANNEL_FAILURE`.

## Security

**Threats.**

* **A network attacker** reaches the SSH domain's Erlang protocol code
  and, through `crypto`, OpenSSL's key exchange and signature code. The
  protocol's parsers are Erlang, so a malformed message ends a connection
  process; a memory error in OpenSSL or the `crypto` NIF takes the whole
  SSH domain. It reaches the system domain only through the login
  facet's five operations and their bounded inputs, and the vault
  only with a user name and a passphrase.
* **A compromised SSH domain** sees the plaintext of every live SSH
  connection and can type into every tty it masters, so it acts as each
  principal logged in through it while that login lasts, as the web
  domain can for its lines. It can sign as the host while it runs, and so
  complete an exchange as this machine with any client that accepts this
  machine's host key, whether the client dialled this machine or a server
  that relays the client's connection here: a client that trusts the key
  for this machine's name, or that accepts it on first use for a name it
  has not seen. Such a client's login is a login through it, as with any
  server whose host key an attacker holds.
  It cannot start a session for a principal whose client makes no
  exchange with it while it runs: a signature made at another server, or
  for an exchange whose cookie is spent, expired or not the facet's,
  opens nothing ([Logging in](#logging-in)). It cannot read any key, or
  reach any principal's files except through a shell it can type into.
* **Credentials typed through the SSH domain outlive its compromise.** A
  compromised SSH domain reads every passphrase given through it, at
  `keyboard-interactive` and at every tty it masters, where `sshkeys add`
  asks for one. With a passphrase it can log in as that principal later,
  and it can type `sshkeys add` with a key of its own into a session's
  tty. Restarting the SSH domain from its image ends neither. Keeping
  private keys in the vault does not prevent this: the passphrase and the
  login keys are the principal's way in, not keys the vault uses. The
  principal recovers by changing the passphrase from a session the SSH
  domain does not carry, at the console, and by listing the login keys
  with `sshkeys` and removing those it did not add; the principal
  service's log names each addition with its fingerprint and line
  ([Logging](#logging)).
* **A compromised session domain** holds its own line and its ttys; it
  cannot add a login key without the passphrase or reach another
  principal's session.
* **A stolen login key** logs in as its principal, and its session uses
  the principal's vault keys while another session holds them open
  ([Logging in](#logging-in)); `sshkeys del` refuses it every later
  login, and a session it started runs until it ends.
* **Key theft.** The host key and every private key are the vault's
  (stage 4), and the login keys are public. Before the vault the host key
  is a file of `/data/ssh`, which the SSH domain reaches through
  `ssh_state` and whoever reads the data partition reads, in development
  builds only. The development login
  key's private half is held only by the host that built the image, in
  its clone's owner-only key directory: no image, receipt or log carries
  it, so whoever holds that clone's key directory logs in as `root` to
  every development image the clone builds for a harness, and to nothing
  else.
* **Root's keys on the medium** (before the vault). Whoever can write the
  medium adds a login as `root`, the known limitation above. While the
  machine runs no domain can write the file, and the manifest check makes
  the domain that reads it the only one that can publish root's keys, but
  its keys are as sound as that storage domain: that domain serves `system` to
  every domain, so a flaw in it that a client's requests could steer
  would be a way to root's login. Development builds run trusted code
  only; the dependency is a security residual in `TODO.md`.
* **Downgrade.** The lists are fixed and no SHA-1 signature, CBC cipher or
  finite-field group is offered. The strict key exchange holds for every
  client that offers it; a client that does not is exposed to the prefix
  truncation it closes, and its log record says so.
* **Timing.** The key exchange, ciphers and the host key's signing are
  OpenSSL's constant-time code
  ([design-crypto.md](design-crypto.md#cpu-features-and-constant-time)).
  The facet's work is on public data, the exchange's shared secret aside,
  which it only hashes. `key_ok` answers the same for an unknown
  principal as for an unknown key; its timing is not equalized, and
  principals' names are not secret, since the manifest lists them.

**What OpenSSL's code can reach** in the SSH domain is that domain: its
memory, which holds every connection's session keys and data, its
grant's sockets, its login facet and its host key facet. No mapping is
writable and executable, and OpenSSL makes no code.

## Verification

Each test names the seeded failure that proves it ran. The facet's
decisions are pure functions of their inputs, the outstanding cookies,
this machine's host key and the principal's key list, so they are tested
on the host, and so are the manifest check's rules, the storage domain's
reader and its lifecycle; the QEMU suite runs the interop and the ends.

**Oracles.** OTP's `ssh` suites run through `make check-oracle` and
agree case by case with stock OTP 29.1.2, so the edits change nothing for
stock callback modules. The host's OpenSSH client, its version recorded
in the run, is the interop oracle, through QEMU's forwarded port. RFC
8032 section 7.1's Ed25519 vectors are the verifier's.

**Fuzz targets.** OTP's parsers are tested by OTP's suites;
`erx_ssh_wire` and `erx_boot_keys` are the parsers erXos writes for SSH,
and `sshkeys` parses its key line with OTP's `ssh_file`. The targets:
`erx_ssh_wire` (blobs and exchange inputs: no crash,
`badarg` for what does not fit, every accepted blob re-encodes to its
input and every accepted exchange input's five strings to its prefix);
`erx_boot_keys:decode/1` and the FAT lookup (no crash, every blob 51
bytes of the key blob's layout, checked by the target's own matcher
rather than the decoder's, no lookup past 32 clusters); and
`erx_login:medium_keys/1` (no crash on concatenations of up to 1 KiB;
every accepted list at most 16 keys, none of small order; a length not a
multiple of 51 or past 816 bytes refused).

| `erx_fat_read:root_file/3`, over volumes fsimg writes: the long name is found, and as `AUTHORIZED_KEYS`; a file answers its size, never its slack; deleted entries, `authorized_keys.pub`, a directory and a long name with a wrong checksum are not found; a file in the record's erase unit is; bad chains and a size past 16 KiB give `does not read` or the bound; a boot sector that does not fit the record gives `not its FAT volume` | the link range check removed: the case raises; the deleted-entry marker not checked: the deleted file is found; the last cluster answered whole: the slack's key line is returned |
| the fuzz targets of the decoder and the lookup | the range check on a FAT link removed: a mutated link crashes the lookup within the budget |
| the fuzz target of `medium_keys/1` | the bound taken as 17 keys' length: a 17-key input is accepted; the small-order check skipped for the last blob: a list ending in the neutral point is accepted |
| no domain writes the file: every record-partition window but `boot_selection` and `reset_count` refuses a write, and those two answer `erange` outside their sector | the table's single window over the whole partition kept: a write to the root directory's sector succeeds |
| the facet's read of `login_keys`: a bad length, more than 16 keys, another type or the neutral point refuses the whole file; an overstated size reads two keys; an endless file is read for 817 bytes; an oversized reply gives `eio` and keeps no copy | the small-order check skipped: the neutral point is admitted; the facet reading with `file:read_file/1`: the server counts reads past 817 bytes |
| root's keys end to end (QEMU): the development key in the record volume logs in; the line prefixed by `restrict` is refused with `line 1: not a plain ssh-ed25519 key`; no file shows `root has no SSH login key` | the image build writing the key into the system release instead: the first case fails |
| login keys (stage 4): `sshkeys add` needs the passphrase, `sshkeys del` removes at once, a key written to the medium by hand under `device` does not open | the add path skipping the passphrase check: the wrong passphrase succeeds |

The Raspberry Pi 4 guide has the user write `authorized_keys` onto the
card's `ERXOS` volume before the first boot
([What is on the card](guide/raspberry-pi-4.md#what-is-on-the-card)).
That macOS's Finder, Windows and Linux write the file under its long name
is unverified until a manual pass on the board writes it from each,
boots the card and logs in.

## Alternatives considered

* **The daemon in the system domain.** Rejected: it would put OpenSSL and
  a network parser into the trusted base, against the existing decision.
* **The daemon in the network domain.** Rejected: that domain parses
  every packet and calls no OpenSSL
  ([design-crypto.md](design-crypto.md#domains-that-call-no-openssl)).
* **A domain per connection**, as OpenSSH separates each connection's
  process. Rejected for now: each login already gets its own session
  domain, so a compromise from one connection reaches other principals
  only through a memory error in the SSH domain's OpenSSL or NIF, and the
  protocol parsing itself is Erlang; a domain per connection would cost a
  runtime per connection and a way to hand an accepted socket and its
  key exchange to another domain, which nothing provides.
* **The SSH transport moving into the session after login.** Rejected:
  OTP's connection state cannot be handed between domains, and the
  pre-login half would still need the SSH domain.
* **The session identifier on the SSH domain's word, refused when seen
  before.** Rejected: a signature the principal made at any other server,
  for an identifier never seen here, would open a session, and the record
  of identifiers seen grows with every login and must outlive the facet's
  restarts.
* **OpenSSH's monitor rule**, the session identifier as the first hash
  the host key signs for the connection (`monitor.c:767-772`). Rejected:
  the SSH domain would still choose that hash, as the monitor's own
  comment says (`:739-741`).
* **The vault deriving the session identifier**: its host key facet
  issuing the cookie and checking the exchange input against its own key
  before it signs, and the login facet accepting only an identifier the
  vault signed. Not adopted: it is the same check, in the domain that
  holds every logged-in principal's keys, with each exchange input hashed
  there, and it makes every key login a question to the vault. What it
  adds, a host key that signs only exchanges begun with its own cookie,
  does not limit a compromised SSH domain, which can ask for cookies.
* **`ecdh-sha2-nistp384` and `ecdh-sha2-nistp521` offered**, with
  SHA-384 and SHA-512 exposed to the login facet. Not adopted: the
  Ed25519 verifier already computes SHA-512, and SHA-384 is its
  processing with other initial values, so the cost is not new hash code
  but a choice of hash by exchange method in the facet and the tests of
  each, for exchanges a client with FreeBSD's default list never needs,
  since it offers the Curve25519 exchanges and `ecdh-sha2-nistp256`
  before them ([Algorithm policy](#algorithm-policy)).
* **Signatures checked in the vault with OpenSSL**, which would admit RSA
  and ECDSA login keys. Rejected: it would put network bytes into the
  domain that holds every logged-in principal's keys.
* **`~/.ssh/authorized_keys` on the data partition**, FreeBSD's default.
  Rejected: whoever writes the data partition or runs in the session
  could add a login, which the vault's design refuses for every other
  credential.
* **Root's `authorized_keys` on the booted slot's boot partition**, the
  volume holding `config.txt`, where Raspberry Pi OS takes its own
  first-boot files. Rejected: an update replaces that partition whole,
  so the keys would vanish at the first update unless the slot writer
  parsed FAT to carry them; the check of a slot hashes the partition
  whole; and no domain parses a boot partition's FAT.
* **The system domain decoding the file's lines**, or the image build
  writing raw blobs beside the line. Rejected: the first puts a base64
  decoder and a line parser of text from the medium into the trusted
  base; the second gives the file two forms a user must keep in step,
  and a user writing the card has only the line.
* **Bad-cluster marks over the rest of the record's erase unit**, so no
  FAT writer puts a file beside the record, and a reader that refuses a
  file there. Rejected: they cost 1 MiB of the 5 MiB volume, a range
  option of the FAT tool, a read-back of the marks in the image build
  and a range check in the reader, and a host's repair tool may clear
  them, after which the reader would refuse the file a user copied. A
  host writing beside the record can tear the record, a card pulled
  mid-copy among the ways, and the card is then written again: a residual
  in `TODO.md`. The keys are read from the medium only until the first
  boot imports them.
* **Reading the medium's file at every boot**, with no home copy.
  Rejected: the record volume would be read and decoded at every boot,
  a key could be changed only by writing the card on another computer,
  and Raspberry Pi OS, whose users this follows, imports its first-boot
  files once.
* **The slot writer reading the file**, since it already holds a window
  on the record partition. Rejected: the domain that writes slots would
  parse a volume anyone with the card can craft, against ST-R4 of
  [design-storage.md](design-storage.md#requirements).
* **The daemon's word for who logged in.** Rejected: a compromise of the
  SSH domain would be a login as anyone.
* **Dropping the SHA-1 MACs.** Not adopted: FreeBSD offers them, after
  the SHA-2 ones, and the AEAD ciphers that come first use no MAC.

## Risks and open questions

* **Ed25519-only login keys**, for S3: RSA and ECDSA users use the
  passphrase method or make an Ed25519 key. FIDO keys
  (`sk-ssh-ed25519@openssh.com`) are not accepted, a planned feature in
  `TODO.md`.
* **Passphrases over SSH** are on, as FreeBSD's keyboard-interactive is,
  under the vault's network limit; a manifest argument turns the method
  off.
* **Typed-ahead input is lost past the tty's bound**, as at the console;
  a paste larger than the bound into a program that is not reading loses
  bytes. An acknowledgement of input in the console interface would carry
  the SSH window to the tty; recorded in `TODO.md`.
* **OTP sets a channel's window and packet from the socket**, whatever
  receive buffer the system reports and at most 64 KiB
  ([Context](#context)), with no option for
  [Limits and who pays](#limits-and-who-pays)' 64 KiB and 32 KiB, so the
  SSH domain needs an edit to OTP's ssh, a daemon option for the
  window and packet a channel offers, before its worst case is the
  40 MiB that table counts; the item is in `TODO.md`.
* **A job's printers are bounded per process, not per channel.** While
  the client takes no output, the job's group holds one output request
  and each printing process at most one more in the group's mailbox,
  fewer than stock OTP's group, which forwards every request to its
  driver at once. How large a request is, how far a format expands it and whether
  a function it names returns are the printing process's own code, the
  session's, which the client cannot change; a client that stops reading
  only stops the printers, and its hangup ends the group whatever it is
  running. A bound per channel would need the printers to wait before
  they send, which the io protocol does not offer.
* **How a job's messages reach their job.** The channel's `job_input`,
  `job_eof`, `job_sent` and `job_hangup` must reach the job they belong
  to, of up to ten on a connection, and none may be lost: a lost
  `job_eof`, `job_hangup` or `job_sent` leaves a job stuck. Through the
  line's facet they would arrive by `message/2`, which names the grantee
  but not the sender, and the facet drops such a message once `in_flight`
  forwards are outstanding
  ([design-system.md](design-system.md#a-sessions-lines)), so routing
  and delivery are settled together, and `open_job` and these messages
  stay out of `tty_line`'s interface until they are. Two ways fit what
  exists: `open_job`'s answer hands the channel the job's relay, a
  process acting for the facet's grantee as a web view does, which takes
  the four messages from its grantee alone, ends with the facet and is
  bounded by the one unanswered message each way the table above holds;
  or the messages keep going through the facet, tagged with the alias the
  channel makes for the job, as stage 1's relay takes them
  (`erx_ssh_job`), bound to the admitted grantee and a live job, with an
  admission that never drops one of the four. Recommended: the relay as
  the endpoint, which needs no change to the facet behaviour and routes
  by the process the message is sent to.
* **Session creation per login** costs a domain's start; the latency of
  an SSH login is on the watch list
  ([todo-performance.md](todo-performance.md)),
  settled by `tools/erx bench ssh-login`.
