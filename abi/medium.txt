# The boot medium's layout (docs/design-storage.md, "The boot medium's table"), in
# 512-byte sectors, the one source of where each partition lies. The master boot
# record at sector 0 names the boot-selection record's partition, slot A and slot B
# in its first three entries and the extended partition in its fourth. The extended
# partition starts with the vault's extended boot record, whose first entry names the
# vault's partition and whose second names the data partition's extended boot record;
# the data partition's record names the data partition alone. Every partition but the
# data partition has a fixed start and length; the data partition has a fixed start
# and runs from medium_data_sectors_min sectors to the medium's end, and the extended
# partition ends where it ends. Every boundary is a multiple of 2048 sectors (1 MiB).
# Every entry's status is mbr_status_inactive. Inside each slot, the slot's bootable
# file starts medium_slot_boot_start sectors from the slot's first sector, so the QEMU
# harness finds it without parsing the slot (docs/design-platforms.md, "Slots and the
# boot-selection record"); the 4 MiB before it hold the slot's FAT's boot sector,
# reserved area and tables, which slot A's FAT32 of the slot's first 128 MiB with 1 KiB
# clusters fits (tools/lib/erx/pi_medium.rb).
#
# The record partition (docs/design-platforms.md, "Slots and the boot-selection
# record") is one FAT16 volume laid out in MiB regions, so that the reset count and the
# boot-selection record each have an erase unit of their own. Counted from the
# partition's first sector: MiB 0 holds the boot sector and the start of the reserved
# area; the reset count is the sector medium_record_count_start, the first of MiB 1,
# inside the reserved area, which no FAT reader reads; MiB 2 holds the end of the
# reserved area, both FATs and the root directory; and the record is the sector
# medium_record_select_start, the first of MiB 3, where the data area starts, the one
# 512-byte cluster of the volume's autoboot.txt. The data area fills the partition's
# last 5 MiB, 10,240 clusters of 512 bytes, which makes the volume a FAT16 by its
# cluster count. The partition starts 1 MiB into the medium, so it ends 9 MiB in, and
# slot A starts 12 MiB in. Firmware names a slot by its partition's number, its entry's
# index in the master boot record counted from 1: medium_slot_a_partition and
# medium_slot_b_partition. The record has exactly two encodings, medium_record_a while
# slot A is committed and medium_record_b while
# slot B is, each followed by zeros to the end of the sector; the two have the same
# length, since a commit rewrites the sector and never the FAT's directory entry that
# records the file's length. Each is the Raspberry Pi firmware's autoboot.txt naming
# the committed slot's partition, and the other slot's in its [tryboot] section;
# medium_record_a's text is, line by line, "[all]", "tryboot_a_b=1",
# "boot_partition=2", "[tryboot]", "boot_partition=3", each ended by a line feed, and
# medium_record_b's swaps the two numbers.
