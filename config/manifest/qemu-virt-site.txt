# The website's manifest of QEMU virt: the system the erXos website boots in v64,
# the browser's emulator of an AArch64 virt machine (site/README.md), from the image
# `tools/erx boot --without-web` builds. It is the development manifest,
# config/manifest/qemu-virt-development.txt, without the web and display domains: the
# page has no host link, whose web facet is all the web domain serves, and no gpu for
# the display domain to drive, and each domain would only cost boot time on the
# emulator's one core. Every other record is the development manifest's, whose
# comments give each row's reasons; where they reckon root_memory and the two domains'
# shares of it, take the figures below instead.
#
# Leaving the web domain out removes its share, runtime limits, limits and domain
# records, its relay service and the system domain's facet of it; leaving the display
# domain out removes its share, runtime limits, limits and domain records, its window
# tree's service and display record, and the display unit it holds. That shrinks what
# the system principal holds by the room they took: its memory and root_memory each
# lose the web and display limits' 24 MiB and outer 1 MiB each, and root_memory the
# display unit's 9 MiB of DMA memory as well, which the domain library charges to the
# system's budget; its domain quota and max_domains each lose two domains; and
# max_connections loses the two domains' system connections. The 59 MiB root_memory
# gives up stays outside the root's memory; no domain gains it. The 250 mcpu the two
# shares took is what the system share's reserve leaves free for the medium boots' test
# rows (MediumBoot::EIGHTH_SHARE).
# The image is packed and checked on the site machine (ProductionImage::Machine.site),
# the RAM site/terminal.js gives the website's guest, less than the development machine.
#
# The image's build admits this file with the same manifest check as the development
# manifest, so the check proves what the website ships.
# test/host/interactive_boot_test.rb holds its records equal to the development
# manifest's less the web domain's six, the display domain's seven and the room they
# took, so a change to the development manifest fails that test until this file takes
# it too.
#

# data: one erx_fs grant of /data's tree for each grantee, read-write and bound to the
# grantee's domain id. Its max_request is files_max_frame_min (property 16), not the
# largest 9P msize, 65560, since a request is measured as its encoded Erlang term, which
# for a 64 KiB write with its envelope is longer than that; in_flight caps the requests the grant holds at once; max_heap_size, in
# words (2 MiB), bounds the grant's process, which holds up to in_flight write requests of
# 64 KiB with their data. reductions and period_ns bind no erx_fs grant. The storage
# domain takes two connections, root's session and one more while a session is replaced,
# and root's session four: data, net, and one more for each while its server is
# replaced; a domain's system connection counts against no quota (life_connections,
# liberx/system/dom_life.c). The network domain, like the storage domain, takes two.
# The machine's max_connections, 10, holds the five rows at rest (the system
# connections of root's session and of the two configured domains, and the session's
# data and net), the three a replacement session makes beside its predecessor's
# closing rows, and the two a restarted configured domain makes beside its own.

  server @domain.storage
  interface files

# inspect: the inspector's queries for each session made from root's template
# (docs/design-live.md, "The inspect service"), served by the system domain, so it
# travels on the session's system connection and takes none of max_connections. A
# request is a path and its options within 4 KiB; in_flight is the design's default of
# two query workers at once; max_heap_size, in words (512 KiB), bounds the facet's
# process, which holds the requests in flight, not the answers.
