# The development manifest of the Raspberry Pi 4 Model B on the stopgap
# (config/platforms/raspi4b.json; docs/plan.md, 1b-I's stage (a)): the system domain
# alone, with the system principal's session template, from which the console starts
# root's session at boot (docs/design-system.md, "Booting"). It configures no domain:
# the Pi's storage, network and display domains come with stages (b), (c) and (d).
# No unit record here places the platform record's Ethernet unit, net, so no domain holds GENET,
# nor its SD unit, sd: the unit's legacy SD controller is of no kind a runtime drives, and
# the domain library refuses a configured domain that holds such a device (TODO.md, "the
# Raspberry Pi 4's sd unit").
#
# The system domain holds three units (docs/design-platforms.md, "Raspberry Pi 4 Model B"):
# two of one register page of the board each, the console's, the mini UART's page, which
# it shares with the auxiliary SPI controllers that no driver here drives, and the host
# link's, the PL011s' page, of which the host link uses UART3; and the framebuffer's, so
# the root reads the framebuffer the firmware set up and prints its line
# (docs/design-device-tree.md, "The lines") and the system domain finds its record. No
# runtime here drives the framebuffer. The console's driver is erx_mini_uart, which keeps
# the divisor the firmware set.
#
# The shares, runtime limits and the session's limits are QEMU virt's development
# manifest's (config/manifest/qemu-virt-development.txt), whose comment gives their
# measurements. The session's network client looks for its net facet as on QEMU virt; no
# domain serves one here, so its sockets answer enotconn. The system principal holds root's one session, 36 MiB and outer
# 1 MiB, and 1 MiB for the outer budget of a session that has ended while the system
# domain still holds a connection to it, as QEMU virt's comment explains. The system
# baseline is QEMU virt's 46 MiB. root_memory, 128 MiB, admits the baseline and the
# principal's 38 MiB with 44 MiB no one is promised, and lies well below what the
# smallest Pi 4 the record names leaves the root.

# apps: the start service's tree, /apps/ctl and /apps/rc.conf (docs/design-apps.md,
# "Interfaces"), for each session made from root's template: one erx_fs grant served by
# the system domain, bound to the session and ending with it, so it travels on the
# session's system connection and takes none of max_connections. Its max_request is
# files_max_frame_min (property 16), as for every files grant; a ctl write is one line of at most
# 4 KiB and rc.conf at most 64 KiB, so in_flight is small; max_heap_size, in words
# (1 MiB), bounds the grant's process, which holds rc.conf's text while it answers.

  server system
  interface files

  service @service.apps
