# The Raspberry Pi 4 Model B's part of its development manifest on Fiasco
# (config/platforms/raspi4b.json; docs/plan.md, 1b-I). The manifest is the records every
# board takes, config/manifest/development.txt, followed by these (Platform#manifest_source).
# Together they configure the system domain, seven configured domains, storage, network,
# display, pcie, usb, media and bt, and the system principal's session template, from which the console
# starts root's session at boot (docs/design-system.md, "Boot"). This part holds the
# machine, the system principal, the apps row, the display domain's limits, the units and
# windows of the board's devices, the network domain's row, whose driver is the board's,
# the USB domain's rows, the media domain's and the Bluetooth domain's. The common part holds the storage, display and PCIe domains'
# rows, the shares,
# runtime limits and the other limits, and the services and facets; QEMU virt's part
# (config/manifest/qemu-virt-development.txt) gives their measurements.
#
# The storage domain, an interpreter service domain, holds the platform record's sd unit,
# EMMC2 and the legacy SD controller that shares its line (docs/design-storage.md, "The SD
# controller's line"). The unit is named block, as on QEMU virt, because storage_ctl acts
# on that unit name. The legacy controller is of no kind a runtime drives, so the domain
# holds it with the unit and is given no record of it and no register window onto it, and
# no driver opens it (docs/design-shared-devices.md, "The unit rule"). erx_blk drives
# EMMC2's sdhci record with its SD device process (erx_blk_sd), which logs that the SD card
# is not driven when no card answers. The domain holds the card's data window and serves
# /data, littlefs on that partition, as the data facet. A boot with no card on EMMC2 has no
# volume, so the storage domain provides no mint for data, the grants stay idle and /data
# answers eio.
#
# The system domain holds six units (docs/design-platforms.md, "Raspberry Pi 4 Model B"),
# of one register page of the board each: the console's, the mini UART's page, which it
# shares with the auxiliary SPI controllers that no driver here drives, and the host
# link's, the PL011s' page, of which the host link uses UART3, both in the common part; and
# rng, the RNG200, which no runtime drives and the root reads itself at boot when /chosen
# carries no seed, at the window its row in the platform record states and only when the
# firmware's tree names that window (docs/design-fiasco.md, "The Raspberry Pi 4", its
# entropy item); and watchdog, the power-management block's watchdog, which no runtime drives
# either and the root's watchdog thread arms and reloads, at the window its row states and only
# when the firmware's tree names that window (docs/design-platforms.md, "The watchdog"); and
# mailbox, the firmware's mailbox, which no runtime drives either and only the root maps, at
# the window its row states and only when the firmware's tree names that window, for the
# firmware requests it sends (docs/design-fiasco.md, "The call table", erx_firmware_request;
# docs/design-kernel.md, "Firmware requests"); and gpio, the pin controller, which no runtime
# drives either and the root writes once at boot, before any domain starts, setting the
# functions of the on-board pins the manifest's pins rows name, UART0's to the
# Bluetooth controller, at the window its row states and only when the firmware's tree names
# that window (docs/design-header-io.md, "On-board pins"); property 8 lets the system
# domain hold it, since its registers set the console's pins. The console's driver is
# erx_mini_uart, which keeps the divisor the firmware set.
#
# The display domain holds the framebuffer's unit and runs the firmware framebuffer's
# driver, erx_firmware_fb, and the window system's screen (docs/design-display.md, "The
# display device"): the root reads the framebuffer the firmware set up, prints its line
# (docs/design-device-tree.md, "The lines") and writes the display domain its record, so a
# screen on HDMI 0 shows the display's windows, the dashboard's on the card, which carries
# the kiosk enabled (the apps row below). A boot whose firmware set up no
# framebuffer, QEMU's raspi4b model without the raspi4b suite's stand-in for the firmware
# among them, gives the domain no framebuffer record, and the domain runs without a
# screen. Its 40 MiB is QEMU virt's 24 MiB, which holds no screen image there, the gpu's
# being device memory, and 8 MiB for the screen image erx_firmware_fb keeps in the domain's
# own memory, one 1920x1080 screen of 32 bits (8,294,400 bytes), with 8 MiB of headroom; a
# larger screen, 4K's 31.6 MiB among them, does not fit, and the driver ignores it. Its
# outer budget is 1 MiB and one pixel area of windows_pixels_default, 8 MiB, with its
# 4 KiB lane, for the apps row's one app, and nine more for the sessions of root's
# template that the system principal's domains quota lets live at once, which display_root
# grants the display (development.txt), 72 MiB and 36 KiB; its quota of four connections is that
# app's, root's session's, its replacement's and the USB domain's input tree's.
# Its memory and the display share's 100 mcpu are measured on neither board (TODO.md).

  outer 84975616

# network: QEMU virt's network domain row for row (config/manifest/qemu-virt-development.txt,
# whose comment explains its memory, connections and restarts), an interpreter service
# domain that holds the net unit, the platform record's GENET (docs/design-platforms.md,
# "The Ethernet controller's unit"), and runs the network stack
# (docs/design-network-stack.md, "Who holds the network device") over erx_genet, whose
# interface is genet0, as FreeBSD names genet(4)'s first unit. It serves net, a grant of
# the stack, to the system principal's sessions, since the system domain may hold none
# (docs/design-system.md, property 15), and network_ctl, its driver-control facet, which
# acts on genet0's link, to the system domain alone (property 8).
#
# Its 36 MiB is QEMU virt's measurement of the stack over erx_virtio_net; the stack over
# erx_genet is not measured on the Pi (docs/todo-performance.md).
#
# Its grant is the users share, 900 mcpu of the 2,325 mcpu the system share's reserve
# leaves the configured domains (dom_system_reserve, liberx/system/dom_core.c).
#
# Its quota of two connections holds root's session and one more while a session is
# replaced; its system connection counts against no quota (life_connections,
# liberx/system/dom_life.c). At rest the machine holds 13 of the 20 these rows take: the
# system connections of root's session and of the storage, network, display, PCIe, USB,
# media and Bluetooth domains, the session's data, net and media, the display's usb_input
# and the media domain's drive grant; the other seven are the four a replacement session
# makes beside its predecessor's closing rows and the three a restarted configured domain
# makes, the USB domain's system connection, usb_input and drive grant, as on QEMU virt. The apps row's one app takes four more (the apps row's comment).

  principal @principal.system
  limits @limits.network
  kind service
  flags none

  release @artifact.network

  restart_period_s 600
  args "-- -root / -bindir /bin -progname erl -home / -nouser -nocookie -no_epmd -proto_dist erx -erx_net interfaces {erx_genet,interfaces,[]} -erx_net runtime erx_net_erxos"
# ntpd, the network time client (docs/design-time.md, "Configuration"): the board has no
# real-time clock, so its wall clock starts at the build's date, and this development
# image is the one exception to the design's decision 1, no default server: it enables
# ntpd with pool.ntp.org, whose first sample the clock service steps to from the
# approximate start. Principal ntpd holds one session of the common part's session
# limits, its memory and its outer budget, on the users share, so root_memory, max_domains
# and max_connections each grow by that session (its system connection and its net
# connection). The template's
# release is ntpd's (ReleaseFiles::RELEASE_SCRIPTS), its -eval starts erx_ntpd, and its
# environment sets ERX_START_FLAGS, standing in for the start row's flags until the start
# table carries them (docs/todo-runtime.md, "time, ntpd"). ntpd_net grants the network stack with small
# limits: two sockets (docs/design-time.md, "Who does what"), a lookup's UDP socket and
# the TCP connection inet_res opens beside it for a truncated answer, while an exchange
# holds one socket alone; 128 KiB of buffers, the least a row may state and that
# connection's; and two requests in flight; ntpd_clock grants the clock interface's
# sample operation alone, so ntpd measures and the clock service decides.

# The Bluetooth domain's rows (docs/design-bluetooth.md, "The Bluetooth domain"): a service
# domain whose release's boot script, bt, starts crypto and erx_bt, so the mint of ble
# exists before init's ready report, and whose -eval (erx_bt_top:start_stack/0) starts the
# rest of the stack once init holds the ready answer's facets, the line grant among them.
# The service ble, which the domain serves, has one grant here, bleuart_ble, so bleuart's
# session is the one domain that holds ble on this board; its row makes the domain
# service accept the mint the domain names. The domain's connections quota of 2 is that
# session's ble connection and its successor's, admitted while the Bluetooth domain still
# answers the end of the one before. They are
# the rows of QEMU virt's Bluetooth suite (tools/lib/erx/bt_domain.rb, whose comment
# explains the runtime limits, the share and the limits) with four differences:
#
# * runtime: the BeamAsm image, as the design names, where the suite runs the
#   interpreter; its 32 MiB and its boot time are measured on BeamAsm on neither board;
# * args: no name, so it advertises its default, the host part of its node name, erxos,
#   and no patch, which no Pi 4 image carries (docs/todo-bluetooth.md, "the Pi 4's
#   patch"): the controller's ROM advertises and accepts a connection without one
#   (docs/research-bluetooth-pi4.md, B-P3 and B-P4);
# * restarts: 5 in 600 s, so the domain service restarts it within its intensity
#   (docs/design-bluetooth.md, "Failure handling");
# * the line grant's device: UART0, below.
#
# Its system connection is one more of the machine's max_connections; the line grant,
# of a system-domain service, travels on it.
#
# line: the controller's line (docs/design-bluetooth.md, "The controller's line"):
